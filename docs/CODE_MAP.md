## `base/cyberscore_try.py` — ⭐ live runtime (28 997 строк)

> Не читай целиком. `rg`/`grep` по имени функции + точечное чтение по диапазону.

Главный модуль: live-парсинг драфтов (CyberScore через Camoufox; DLTV api/html fallback), bookmaker prefetch (Camoufox subprocess + Selenium fallback), draft-метрики, networth/STAR/tier gates, ML phase-wrapper, team-kills≥27 shadow/изолированный Telegram sender, dispatch в основной Telegram (+ VK mirror), runtime-менеджмент (lock, sharded/sqlite stats, delayed-очереди, recovery journal).

### Entrypoint (строки ~28820–28997)

**Kills-window policy** (`KILLS_WINDOW_POLICY`, `_kills_window_policy_select`) — единственный путь отправки kills-ставок. 4 валидированные AND-связки «окно + полоса отправки + второй гейт»:

Рынок окна закрывается **за 2 минуты до его старта**, поэтому полоса отправки идёт от дедлайна предыдущего окна до своего:

| окно | полоса (игровое время) | дедлайн рынка | `min_ed` | второй гейт | WR @1.8 на карту |
|---|---|---|---|---|---|
| `5_15` | 00:00–03:00 | 03:00 | 0.3 | NW-лид > 0 **и** `lane_kills_adv_dict` ≥ 0.2 того же знака | 74% |
| `10_20` | 03:00–08:00 | 08:00 | 0.2 | NW-лид таргета ≥ +500 | 72% |
| `15_25` | 08:00–13:00 | 13:00 | 0.2 | NW-лид таргета ≥ +1000 | 79% |
| `20_30` | 13:00–18:00 | 18:00 | 0.2 | NW-лид таргета ≥ +1500 | 78% |

Ресёрч 2026-08-04 (1425 Tier-1 карт 7.41+, `runtime/experiments/kills/kills_window_*.py`, отчёты в `runtime/artifacts/kills/`): ничья в окне = луз, безубыток при 1.8 = 55.56%. Сквозная политика «одна ставка на карту» — 675 ставок, WR 75.4%, ROI +35.7% (bootstrap 95% +29…+42%); на отложенных по времени 30% — 190 ставок, 72.6%, +30.7%. Прежние полосы (00:00–02:00 / 03:00–05:00 / 07:00–11:00 / 13:00–16:00) с прежними NW-порогами давали 870 ставок при 69.3% и +24.8% (test 66.4%). `min_ed` не менялся: сам по себе слабый гейт (15_25 при 0.2 = 56.0%, на грани безубытка), но после NW-гейта его подъём режет объём без прироста WR. Для kills-гейта ровный `radiant_lead == 0` не проходит ни на какой минуте — полоса 5_15 начинается с 00:00, где пустой фид особенно част.

Правила выбора:
- **одна ставка на карту** — на окне с МАКСИМАЛЬНЫМ `|expected_diff|` в сторону таргета среди прошедших свой `min_ed` (при равенстве — более раннее окно). `expected_diff` считается по драфту и по ходу карты не меняется, поэтому выбор стабилен; в полосах более слабых окон ставки нет (статус `not_strongest_window`);
- гард «одна ставка на карту» ключуется покарточно (`_kills_bet_dedup_key` = URL без numeric-суффикса `uniq_score`) и живёт до конца процесса; на рестарте дубль ловит реестр отпечатков сигналов;
- NW-гейты требуют **известного** нетворса: пустой фид (`radiant_lead == 0` после `KILLS_NETWORTH_UNKNOWN_AFTER_SECONDS`) → статус `networth_unknown`, ставки нет; в теле сообщения такой лид печатается как `Networth: н/д (нет данных)`.

### Lane kills@10: сбор, backend и live-вывод

- `base/analise_database.py:lanes(...)` сохраняет рядом с прежними `wins/draws/games` командную цель `Δkills@10 = sum(radiantKills[:10]) - sum(direKills[:10])`; для Dire-ориентированных ключей знак разворачивается. Невалидный/короткий kills timeline не портит lane outcome: обычные counters пишутся, `kills10_*` для такой карты — нет.
- Поля одного lane-ключа: `kills10_leads`, `kills10_draws`, `kills10_games`, `kills10_diff_sum`, `kills10_diff_sq_sum`. Отдельного набора дублирующихся ключей и отдельного kills-словаря нет.
- `base/explore_database.py` is sqlite-first: early/late/post_lane primary artifacts are `early_dict_raw.sqlite3`, `late_dict_raw.sqlite3`, `post_lane_dict_raw.sqlite3` with `kv(key TEXT PRIMARY KEY, value BLOB)` + `meta`, format_version `1`/backend `sqlite_kv`; lane primary artifact is `lane_dict_raw.sqlite3` with `stats` + `meta` both `WITHOUT ROWID`, format_version `2`/backend `sqlite_stats`; `stats` has `key`, `wins/draws/games`, five `kills10_*` fields.
- `EXPLORE_WRITE_JSON` default `0`: JSON is neither produced nor required for sqlite-first loading; only setting `1` additionally emits legacy JSON for early/late/post_lane; lane JSON is never emitted.
- Runtime `_sqlite_stats_meta_matches`: sqlite-first (`source_name == *.sqlite3` or no companion JSON) stays valid; legacy meta that points at a sibling JSON is accepted only when `source_size`/`source_mtime_ns` match — mismatch falls back to JSON instead of preferring a stale SQLite.
- Live `calculate_lane_kills_advantage(...)` берёт exact 2v2 для side lanes и exact 1v1 для mid; при нехватке использует 2v1/1v1/synergy/solo fallback с приведением Dire-ключей к Radiant-знаку. Каждый lane оценивает один и тот же team-level target, поэтому lane-оценки не суммируются, а усредняются с весом `games/(games+LANE_KILLS_RELIABILITY_PRIOR)`; lead/draw probabilities используют add-one smoothing `(count+1)/(games+3)`.
- Telegram `Lanes:` получает строку `lane_kills_adv_dict: Radiant|Dire +N.NN kills @10 (lead PP%, C/3)`. Она добавлена в обычные, early-local, standalone lane-adv и pipeline-probe сообщения, но не влияет на сторону, порог или сам факт dispatch.

**Грамматика ключей словарей (`analise_database._add_combinations_to_dict` / `_add_kills_window_combinations`), 2026-08:**
- Неупорядоченная группа героев пишется в ОДНОМ каноническом порядке — `_canonical_group(*tokens)` = `",".join(sorted(tokens))`. Это касается пары врагов в 1v2, пары своих в 2v1, пары `_with_` и трио. Раньше пары писались в обоих порядках побайтово одинаково (42.4% ключей early-словаря), а трио — в порядке игроков из JSON, из-за чего 82.2% трио имели перестановочных близнецов и в своём ключе лежало ~20% выборки набора.
- Записей на матч: early-тип `295 → 175` (solo 10 + 1v2 50 + 2v1 50 + 1v1 25 + with 20 + trio 20). У kills_window та же раскладка `275 → 175`: канонизация ужимает пары, а высвободившееся место занимают **trio** — их раньше не собирали именно из-за раздувания словаря дублями порядка.
- Читатели `_lookup_vs_winrate` / `_lookup_with_winrate` / `_lookup_unordered_combo_winrate` перебирают перестановки и суммируют найденное, поэтому канонический ключ находится и в новых словарях, и в старых двухпорядковых. **`calculate_kills_window_advantage` — единственный читатель, собирающий ключ напрямую; он сортирует токены сам, менять его надо синхронно с билдером.**
- Сборка всегда полная (`explore_database._new_metric_dicts` создаёт пустые словари на шард); инкрементальной догрузки поверх старого словаря нет, поэтому смешения канонических и legacy-ключей не возникает.
- `KILLS_WINDOW_BUILD_HIGH_ORDER` (default `1`) — слои 1v2/2v1 в kills_window собираются. Прод-политика `core_1v1_with` их не читает: fallback-цепочка включается только когда 1v1 и with оба пусты, а на 3000 про-картах × 4 окна таких случаев **0**. Держим их ради политик `first_hit`/`blend_all`/`best_abs` и слоевых A/B; ребилд с `=0` убирает (словарь ужимается со ~2x до ~150x, но слоевые эксперименты на нём не поставить).
- Слой `trio` у kills_window: порядок слоёв `1v2 → 2v1 → 1v1 → with → trio → solo`. trio стоит после `with` (ключей на порядок больше, игр на ключ меньше), поэтому в `first_hit` подхватывает только там, где пары пусты; прод-политика его не читает.
- Проверяется `base/tests/test_dict_key_canonicalization.py` (отсутствие дублей порядка, устойчивость трио к перемешиванию игроков, равенство показаний читателей на каноническом и legacy-словаре).

> **Option C — post_lane `solo` (2026-06):** `post_lane_output['solo']` теперь ЭМИТИТСЯ (раньше был выключен `name != 'post_lane_output'`). Сам post_lane-словарь: cp/synergy/trio на широком окне, а **solo-записи (`{hero}pos{n}`) собираются ТОЛЬКО на последнем version-патче** (`analise_database._add_combinations_to_dict(write_solo=...)`, `LATEST_PATCH_START_TS` из `keys.DOTA_VERSION_PATCH_EVENTS`, сейчас 7.41d=1780531200). **Константы STAR (источник истины для решений):**

Полный snapshot и `synergy_opposes_target` сохраняются в `stake_multiplier_context`, поэтому тот же veto повторно применяется в delayed-пути через `_stake_multiplier_from_context(...)`.

## `base/team_kills25_shadow.py` — target-team kills≥27 shadow + отдельный Telegram

- Срабатывает только для draft-кандидата `early_output` WR60 с `hit_count >= 2`.
- Frozen logistic model использует 95 признаков: прежние 90 draft/ELO-признаков, два confidence-weighted patch-roster (`roster_patch_mean_edge_confident`, `roster_patch_ge27_edge_confident`) и три block-consensus (`blocks_target_count`, `blocks_opponent_count`, `blocks_consensus_target`).
- Block-consensus строится по доступным `early_nw`, `early_win`, `late`, `all`: знак суммы target-aligned метрик задаёт направление блока; consensus=1 только при минимум трёх доступных блоках, если все они направлены на target.
- Artifact: `ml-models/team_kills27/team_kills27_shadow.json`, schema `team_kills27_shadow.v2`; отсутствие/ошибка модели не влияет на основной live-сигнал.
- Audit log default: `runtime/team_kills27_shadow.jsonl`; один record на технический `match_key` за жизнь процесса.
- Для target team считается `roster_kills`: из ELO-снапшота выбираются последние 30 более ранних карт того же `team_id` с overlap текущих account IDs минимум 4/5. Текущая/будущие карты и повторы `match_id` исключаются. Latest-patch sample `n` даёт reliability `n/(n+6)`; model features равны `(mean_kills-27)*reliability` и `(ge27_rate-1/1.8)*reliability`. Raw games хранится в context/Telegram, но самостоятельным model feature не является.
- Telegram anti-duplicate использует стабильный Dota `match_id`, а не меняющийся DLTV `match_key` с score/poll suffix. Перед HTTP-вызовом создаётся durable at-most-once claim в `TEAM_KILLS25_TELEGRAM_SENT_PATH`; legacy-строки с URL автоматически нормализуются.
- При `TEAM_KILLS25_TELEGRAM_ENABLED=1` sender применяет ML threshold и `TEAM_KILLS25_TELEGRAM_MIN_WR`; ручных gates по числу roster-карт или mean kills нет. Roster-контур fail-closed только при недоступном источнике (`team_id`/current IDs/observed time/snapshot); нулевой patch sample сам по себе sender не блокирует, признаки импутируются frozen model.
- Production artifact использует `C=0.003`, выбранный по log loss на old chronological validation из `{0.001, 0.003, 0.01, 0.03, 0.1, 0.3, 1.0}`. Bet threshold не оптимизируется: жёстко фиксирован как `1 / 1.8 = 0.5556`; forward outcomes не входят в fit/выбор `C`/threshold, но forward-диагностика просматривалась при feature research.
- Artifact report при фиксированном threshold: `forward_untouched` — 141 bet / 98 hit, `+35.4u`, ROI `25.1%`; соответствующий frozen production refit на всех old rows (`forward_refit_old_only`) — 156 / 104, `+31.2u`, ROI `20.0%`.
- Полная методика, формулы, chronological splits, consensus/roster замеры, tier-срезы и кейс GLYPH: [`docs/TEAM_KILLS27_EXPERIMENT.md`](TEAM_KILLS27_EXPERIMENT.md).
- Успешные отправки дедуплицируются между рестартами через `TEAM_KILLS25_TELEGRAM_SENT_PATH`.
- Env читаются в двух префиксах: сначала `TEAM_KILLS27_*`, при его отсутствии — legacy `TEAM_KILLS25_*`. Если `TEAM_KILLS27_*` **задан**, он выигрывает даже со значением `0`, поэтому kills27-поток выключается независимо от legacy-флага. Имена (суффиксы одинаковы для обоих префиксов): `*_SHADOW_ENABLED=0`, `*_SHADOW_MODEL_PATH` (default `ml-models/team_kills27/team_kills27_shadow.json`), `*_SHADOW_LOG_PATH` (default `runtime/team_kills27_shadow.jsonl`), `*_ROSTER_HISTORY_PATH`, `*_TELEGRAM_ENABLED`, `*_TELEGRAM_BOT_TOKEN`, `*_TELEGRAM_CHAT_ID`, `*_TELEGRAM_SENT_PATH` (default `runtime/team_kills27_telegram_sent.jsonl`), optional `*_TELEGRAM_MIN_PROBABILITY`/`*_TELEGRAM_MIN_WR`. Исключение: `*_SHADOW_LOG_PATH` пока читается только как `TEAM_KILLS25_SHADOW_LOG_PATH`.
- Отдельный `TEAM_KILLS27_TELEGRAM_SENT_PATH` даёт kills27 собственный dedupe-ledger: отправка в kills27-бот не пишет и не читает legacy kills25-файл.
- `base/train_team_kills25_shadow.py` заново строит label `target_kills >= 27`, вычисляет два reliability-weighted patch-roster и три block-consensus признака и обучает artifact на chronological old split; forward не участвует в выборе `C`, threshold всегда равен `1/ODDS`.

## `base/train_public_draft_hero10_experiment.py` — offline public draft experiment

Обучает четыре leakage-safe модели на полном наборе public-карт (v4): `radiant_win_model.joblib`, `total_kills_over_median_model.joblib`, bounded-wrapper `total_kills_regression_model.joblib` и `duration_seconds_regression_model.joblib`; рядом кладёт два энкодера (`win_feature_encoder.joblib`, `level_feature_encoder.joblib`) и `kills_saturation_scale.joblib`. Вход — ровно 10 fixed-position hero IDs (`hero_R_1`…`hero_R_5`, `hero_D_1`…`hero_D_5`); ВСЕ колонки дизайн-матриц выводятся только из этих десяти ID (см. `base/draft_features.py`), ingame-признаки и сторонняя статистика запрещены. Киллы формируются только как сумма `radiantKills` и `direKills` и используются как target. Парсер строго отклоняет неполные драфты, повторные позиции/героев, некорректные kills и duplicate map IDs.

Дизайн под таргет: победа — `hero_role_pair` **signed** (герой + роль + синергия внутри команды + контрпик между командами, ~16.7k колонок); киллы и длительность — `hero_role` **unsigned** (~0.8k колонок). Pair-блок даёт основной прирост по победе (AUC 0.562 → 0.597), по килам и длительности не помогает. Матрицы строятся во float64 намеренно: на float32 lbfgs расходится на pair-ширине.

Хронологическое разбиение: строго 60% train / 20% validation / 20% test по `(start_time, map_id)`. И `manifest.json`, и `results.json` сохраняют для каждого split `count`, `first` и `last` boundary (`start_time`, `map_id`), а код проверяет сортировку и `last(train) < first(validation) < first(test)`. Гиперпараметры (`C`, `alpha`) выбираются только по validation; секция `results.json → evaluation` — метрики модели, обученной ТОЛЬКО на train (сопоставимо с v3), секция `models` — метрики финальной модели, переобученной на train+validation, и именно она сериализуется. Test не используется ни для обучения, ни для отбора. Результаты и модели пишутся атомарно в новый output directory, существующий каталог не перезаписывается.

CLI: `--input-dir` (default `bets_data/analise_pub_matches/json_parts_split_from_object`) и `--output-dir` (default `data/public_draft_hero10_experiment/2026-08-04_all_public_v4`). `train_experiment(matches, output_dir, pair_min_support=30)` — порог поддержки пары в train; на маленьких выборках (тесты) снижается. Запуск только offline через `/Users/alex/Documents/ingame/venv_catboost/bin/python3 base/train_public_draft_hero10_experiment.py`.

## `base/draft_features.py` — сериализуемые энкодеры драфта

`DraftFeatureEncoder.fit(heroes, kind, signed, pair_min_support=30)` → `.transform(heroes) -> csr_matrix`. `kind`: `KIND_ROLE` (`hero_role`) или `KIND_PAIR` (`hero_role_pair`). `signed=True` — победный дизайн: при обмене сторон местами матрица **точно меняет знак** (герой/роль меняют знак, синергия радианта ↔ дайра, контрпик антисимметричен по индексу героя). `signed=False` — дизайн для килов/длительности: при обмене сторон матрица **не меняется**. Неизвестный на train герой не роняет transform — его вклад обнуляется. Пары фильтруются по `pair_min_support` в train.

`KillSaturationScale.fit(kills)` — эмпирическая CDF килов train: `.saturation(kills) -> [0,1]`, `.kills(saturation)` — обратно. Медианная карта → 0.50, p5 → 0.05, p95 → 0.95. MinMax по сырым тоталам так не умеет: train покрывает 6..231 килов, поэтому медиана падает на 0.32, а предсказания зажимаются в 0.17..0.47.

## `base/refresh_public_draft_model.py` — переобучение по патчу + ворота промоута

Одна команда на выход патча: синк корпуса с serv1 → переобучение → сравнение с текущей моделью → вердикт. **Ничего не удаляет, не переключает и не перезаписывает** — промоут остаётся ручным решением, скрипт только печатает вердикт и пишет `refresh_report.json` в каталог претендента.

Главное в сравнении — окно. Гонять претендента по его собственному тесту, а чемпиона по тем же строкам нечестно, когда обучающее окно чемпиона накрывает часть этих строк. Поэтому в зачёт идут только матчи **строго свежее обоих обучающих окон**: публичные — из теста претендента с `start_time > champion_fit_end`, про — с `start_time > max(обоих)`. `fit_end` берётся из `split_boundaries.validation.last.start_time`, потому что финальная модель дообучается на train+validation.

Вердикт `PROMOTE` только когда претендент не хуже там, где данных хватает: по публичному окну всегда, по про-окну — если карт не меньше `--min-pro-rows` (по умолчанию 500), иначе про-гейт явно помечается пропущенным в отчёте, а не проходит молча. Синк — `rsync -az` без `--delete`: на serv1 дедуплицированные файлы усечены в пустышки, и зеркалирование удалений выкинуло бы карты, которые есть только локально.

CLI: `--champion DIR` (по умолчанию свежайший каталог со всеми артефактами), `--challenger DIR` (сравнить готовый каталог вместо обучения — перепроверка прошлого решения без 8 минут переобучения), `--output-dir`, `--no-sync`, `--dry-run-sync`, `--min-pro-rows`.

отбрасываются, иначе второй состав совпадёт с основным). Позиции ищутся только по границам слова

## Политика перезагрузок страницы Winline (поллер текущей карты)

`runtime/winline_current_map_odds_poller.py` опрашивает ОДНУ общую страницу-список.
Перезагрузка стоит десятки секунд, и всё это время в DOM нет ни карточек, ни рынков,
поэтому «рынка нет» само по себе перезагрузку больше не заказывает. Пороги (все
переопределяются через env):

| Константа | env | Значение | Смысл |
|---|---|---|---|
| `RELOAD_AFTER_CONSECUTIVE_MISSES` | `WINLINE_CURRENT_MAP_RELOAD_AFTER_MISSES` | 20 | длина серии промахов до перезагрузки |
| `RELOAD_MIN_SPACING_SECONDS` | `WINLINE_CURRENT_MAP_RELOAD_SPACING_S` | 300 | минимум между перезагрузками одного матча |
| `RELOAD_SETTLE_SECONDS` | `WINLINE_CURRENT_MAP_RELOAD_SETTLE_S` | 30 | окно после перезагрузки, в котором промахи не копятся |
| `RELOAD_STALE_DOM_SECONDS` | `WINLINE_CURRENT_MAP_RELOAD_STALE_DOM_S` | 120 | застывшая подпись DOM = мёртвая страница, перезагрузка нужна |
| `WINLINE_SHARED_RELOAD_MIN_SPACING_S` (cyberscore) | `WINLINE_SHARED_RELOAD_SPACING_S` | 300 | дедуп перезагрузок общей страницы между матчами |

Перезагрузка также сбрасывает счётчик промахов. Восстановление сломанной страницы
не изменилось: невалидная страница по-прежнему идёт через `initial_goto`, ошибки
съёма — через ротацию прокси.

## Промоция матчевого рынка на последней карте серии (Winline)

На решающей карте серии Winline иногда не выставляет рынок карты и оставляет только
«Матч» — там победитель этой карты и победитель матча одно событие (проверено на
живой странице 02.08.2026, REKONIX vs YAKULT BROTHERS, карта 3 при счёте 1:1). В
таком случае кэфы «Матч» подставляются в поток карты.

**Контракт:** матчевые кэфы в поток карты не подставляются НИКОГДА, кроме одного
случая — `series_last_map=True` и рынка карты в карточке нет вовсе.

**Предохранители** (все проверяются по DOM, в плоском тексте трёхисходный «Матч» на
Bo2 выглядит так же, как двухисходный):

- рынок «Матч» должен быть двухисходным (`coefficient-button_generic2`);
  трёхисходный `generic3` (с ничьёй, Bo2) отклоняется;
- карточка сама пишет «3карта» в шапке — требуем совпадения с `map_num`;
- подпись рынка карты должна отсутствовать во всех карточках пары (приостановленный
  рынок карты — не отсутствие);
- порядок сторон выравнивается по тексту карточки (`_winline_team_order`).

**Вычисление «последней карты».** `cyberscore_try._winline_series_last_map` читает
свежий срез SourceTV (`runtime/sourcetv_matches.json`, кэш по mtime) и по
`series_type` (0=BO1, 1=BO3, 2=BO5, 3=BO2) определяет `best_of`. Формат неизвестен
— возвращает `False`. Флаг пробрасывается в `_winline_fast_collect` и далее в
`extract_strict_winline_current_map_odds(series_last_map=...)`.

**Различение «3 карта» vs «3карта».** Строка рынка пишется с пробелом (`3 карта
1.87 1.83`), шапка карточки — слитно (`3карта 28'`). Без этого карточка с
единственным рынком «Матч» выглядела как «рынок карты есть, но без кнопок», и
промоция не срабатывала.

**Тесты:** `base/tests/test_winline_last_map_match_promotion.py` (12 кейсов),
фикстуры `winline_bo2_match_three_way_20260802.html` (Bo2 — запрет) и
`winline_last_map_match_only_20260802.html` (Bo3 — промоция).

Не тронуты: Telegram dispatch, betting gates, dedupe, другие букмекеры,
reload-политика (e647309).

## Multi-agent control plane (отдельно от Dota live runtime)

### `base/agent_workflow.py` — тестируемая state machine

Не запускает агентов. Кодирует контракт `START → PLANNING → WORKING → REVIEWING → APPROVED|REPLANNING`, fan-out и предохранители `stuck`/`cycle`/`limit` (`MAX_FIX_ITERS=3`).

| API | Назначение |
|---|---|
| `parse_worker_message(raw)`, `parse_reviewer_message(raw)` | строгий разбор Worker/Reviewer сообщений; `ISSUES` требует хотя бы один `Critical` с stable `sig`. |
| `WorkflowEngine.start/submit_plan/submit_worker_message/submit_worker_results/submit_reviewer_message/cancel` | переходы состояний; parallel results должны совпадать по числу с `subtasks`. |
| `WorkflowEngine.to_dict/from_dict/save/load` | versioned schema `1`; atomic JSON replace с `0600`, `fsync` и sidecar `flock`. |

### `base/agent_orchestrator.py` — исполняемый Commander

Детерминированно ведёт Planner → Worker waves → Reviewer, сохраняет state и может resume/cancel после рестарта.

| API / input | Контракт |
|---|---|
| `Config.load(path)` / `Config.validate()` | JSON-config; Planner и Reviewer жёстко `gpt-5.6`, effort `high`; Worker default `grok-4.5-fast-high`; `max_parallel_workers` 1..3. `codex_env` передаёт Responses endpoint/auth (в т.ч. OmniRoute), `cursor_proxy_env_file` — env только для Cursor. |
| `validate_plan(plan, expected_base)` | валидирует strict JSON schema, SHA, dependency DAG, safe/non-overlapping `allowed_paths`; возвращает parallel waves. |
| `Commander.run/resume/status/cancel` | state в `<state_dir>/<task_id>/state.json`; integration/worker git worktrees, ветки `codex/swarm-*`, worker commits и deterministic cherry-pick. |
| CLI | `--config PATH run TASK [--task-id ID]`, `resume ID`, `status ID`, `cancel ID`; stdout — redacted JSON state. |

Planner/Reviewer запускаются через `codex exec` в read-only sandbox с `PLANNER_SCHEMA`/`REVIEWER_SCHEMA`; Cursor Worker — в отдельном worktree без shell, с process-group cancellation. **Текущий blocker исходника:** `_prompt()` ожидает `base/prompts/swarm_planner.md`, `swarm_worker.md`, `swarm_reviewer.md`, но этих файлов в текущем дереве нет; до их добавления `run` упадёт до model call.

### `base/swarm_telegram_bot.py` — private Telegram + OmniRoute management

- Long polling; только allowlisted numeric user и private chat. `/run` передаёт задачу orchestrator на stdin; одна задача за раз; `/cancel` посылает SIGTERM process group (затем SIGKILL timer).
- Команды: `/run`, `/status`, `/cancel`, `/accounts`, `/account_add`, `/account_enable`, `/account_disable`, `/account_remove`, `/account_check`, `/confirm`. **`/models` в этой реализации нет**; неизвестная команда возвращает `HELP`.
- `OmniRouteClient` принимает только loopback HTTP, жёстко проверяет version `3.8.46`/schema `1`, скрывает raw account IDs за hash aliases; mutations требуют 120-секундного `/confirm`.
- Env (секреты только в service env): `SWARM_TELEGRAM_BOT_TOKEN`, `SWARM_TELEGRAM_ALLOWED_USER_ID`, `SWARM_ORCHESTRATOR_COMMAND` (JSON argv), `OMNIROUTE_MANAGEMENT_URL`, `OMNIROUTE_MANAGEMENT_KEY`, `OMNIROUTE_EXPECTED_VERSION`; optional `SWARM_CODEX_DEVICE_LOGIN_COMMAND`.

### OpenCode profiles — legacy/альтернативный контур

- `opencode.json`: Commander/plan = `opencode/grok-4.5`; role-prompts в `.opencode/agent/`.
- `.opencode/agent/worker.md` фактически задаёт Worker `opencode-go/glm-5.2`, хотя prose в prompt называет его Grok; planner/reviewer frontmatter задаёт `grok-4.5`.
- `opencode.grok-4.5.json` использует другой model ID: `opencode/grok-4-5`; `opencode.zen-opus4.8.json` — `opencode/claude-opus-4-8` для Commander/plan.
- Эти файлы не управляют `base/agent_orchestrator.py` и не определяют команды Telegram-бота.
