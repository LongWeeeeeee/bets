# E-253. Почему ELO держится в памяти и сколько это на самом деле стоит

- **Дата:** 2026-09-03. Запрос alex: «с чего вообще мы держим elo в памяти? Мы
  изменяем его после каждого матча и считываем в начале карты — для чего держать
  ELo в памяти». Вопрос задан после E-251/E-252, где память снимали по частям,
  не трогая архитектуру.

## Замер (serv1, python 3.12.3, каждый режим отдельным процессом)

```
режим elo:
  после импортов                                   12 МБ
  json.load(live_elo_model_state.json)  15 c     1291 МБ   +1279
  from_state() -> 13 словарей модели     9 c     2604 МБ   +1313
  load_read_model() массивная модель    67 c     3658 МБ   +1055
  load_snapshot() slim-снимок            4 c     4030 МБ    +371
  ИТОГО ELO-подсистема                           4030 МБ

режим arrays:
  load_read_model()                     59 c     1152 МБ   +1140
  данных в массивах: 74 МБ в 18 массивах
    player_global._keys 7.3 МБ, _vals 7.3 МБ
    player_global_last_seen_ts._keys/_vals по 7.3 МБ
    player_current_org._keys/_vals по 7.3 МБ
  разница 1079 МБ — стоимость сборки из JSON

режим prematch:
  PrematchModel(артефакт v3)             6 c      657 МБ    +645

режим snapshot_full:
  json.load(весь снимок 646 МБ)         15 c     1705 МБ   +1693
```

Последняя строка — поправка к E-251: на Mac (python 3.9) полный разбор снимка
стоил 3694 МБ, на проде (3.12) — 1693 МБ. То есть slim-загрузка на боевой
машине сэкономила ~1.3 ГБ, а не 2.87 ГБ; направление верное, число из
локального замера было завышено вдвое.

## Нагрузка против стоимости

| | значение |
|---|---|
| применённых карт в сутки | ~23 (497 за 22 дня базы 11.08) |
| чтений силы состава | сотни в сутки (по числу разобранных карт) |
| данных, которые нужны чтению | рейтинги двух команд и их ростеров — сотни записей |
| держим в памяти | 4.03 ГБ, из них полезных данных 74 МБ |

`array_store` при этом УЖЕ устроен под произвольный доступ: отсортированные
ключи + `np.searchsorted` (`ELO/array_store.py:47-66`), строковые ключи
упакованы 63-битным blake2b. Не хватает только одного — хранить массивы на
диске и читать через mmap, вместо того чтобы собирать их из JSON в процессе.

## Куда это лечится (по убыванию выигрыш/риск)

1. **Ночная сборка .npz + mmap в чтении** (~2.3 ГБ: 1140 МБ массивной модели +
   1279 МБ разобранного JSON, который нужен только как источник для неё).
   Цепочка уже пересобирает и возит снимок (шаг 5c, E-249) — добавить сборку
   .npz из 18 массивов + `np.load(..., mmap_mode='r')` в `load_read_model`.
   Логика чтения не меняется вовсе: `_Sorted._index` уже делает searchsorted по
   `_keys`, а mmap отдаёт те же массивы; в памяти остаются только тронутые
   страницы (чтение карты это две команды и их ростеры — десятки КБ).
2. **Дельта вместо полного состояния.** `live_elo_model_state.json` хранит ВЕСЬ
   model_state (519 МБ) и перезаписывается целиком после каждой карты, хотя
   живой прирост — сотни чисел. Хранить дельту (append-only: изменённые
   player/roster/team значения от базы снимка) и накладывать её на mmap-базу при
   чтении. Охрана уже есть: `base_reference_timestamp` + сигнатура конфигурации
   (`live_team_strength.py:590-603`), а перебазировка при смене снимка —
   `ELO/rebase_runtime_model_state.py` (E-252).
3. **Мутация вне процесса прода.** 1313 МБ словарной модели — это путь записи
   (`from_state` + `export_state`). Применение исхода карты можно вынести в
   короткоживущий подпроцесс (как перебазировка) или в отдельный демон, и тогда
   прод-процесс словарную модель не строит вовсе.

Итог трёх шагов: ELO в проде ≈ slim-снимок 371 МБ + mmap-страницы (десятки МБ)
+ дельта (КБ), то есть **~0.4 ГБ вместо 4.03 ГБ**, и пер-карточный разбор с
сериализацией 519 МБ исчезает вместе с пиками 9-10 ГБ.

## Что нужно для каждого шага

- Parity-харнесс: те же числа на тех же входах, что и сегодня (для пути чтения
  сверка `hybrid_strength` по набору карт; `hybrid_strength` — один из двух
  признаков предматчевой модели с корреляцией 1.0 к обучению, здесь ошибка
  невидима снаружи).
- Прочность при падении: дельта — append + fsync, схема уже отработана на
  `live_elo_progress.json`.
- Наблюдаемость: сообщение «около 340 МБ» в `_report_array_model`
  (`base/win_model_veto.py:510`) заменить на измеренное — иначе следующая
  проверка снова поверит цифре из строки лога.

## Где искать ошибку

- **Если после mmap чтения hybrid_strength поедет** — первым делом сверить
  порядок ключей: searchsorted требует СТРОГО отсортированных `_keys`, а сборка
  .npz обязана сортировать так же, как `array_store._Sorted.__init__`
  (`np.argsort(kind="stable")`).
- **Если дельта вырастет до мегабайтов** — значит в неё пишут не изменения, а
  полное состояние; проверять число ключей в дельте против числа применённых
  карт (порядок: десятки-сотни записей на карту, не сотни тысяч).
- **74 МБ данных** — это сумма `nbytes` 18 массивов, найденных обходом модели
  (глубина 4). Если структура модели изменится, обход может недосчитать: сверять
  число массивов (18) и имена (`player_global._keys` и т.д.).

## Отрицательная часть

Ни один из трёх шагов в этом ходе НЕ сделан: это перестройка живого пути
рейтингов, она требует parity-харнесса до, а не после. Замер — это ответ на
вопрос «зачем держим», а не замена правки.
