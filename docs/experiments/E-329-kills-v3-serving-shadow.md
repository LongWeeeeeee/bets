# E-329. Боевой сервинг kills-v3 для прематч-панели

Продолжение E-328: там модель B (панель 928 колонок + 152 колонки kills-v3 T+P) обыграла прод на всех 6 целях
офлайн. Здесь — как подать те же признаки вживую, чего это стоит и в какой режим выкатывать shadow.

## 1. Пререгистрация (`.omc/decisions.md`, до чисел)

- **Рычаг задержки.** B_d86400 (история видна при `end < start − 86 400`, то есть «только ночной снимок, без
  подкачки карт текущего дня») опровергается как режим сервинга, если `LL(B_d86400) − LL(B_d1200) > +0,002`
  на ≥ 2 из 6 целей.
- **Абляция OpenDota.** B_noOD = B_d86400 без 30 колонок, построенных из метрик, которые есть только в разовых
  выгрузках OpenDota (`obs_placed`, `sen_placed`, `stuns`, `teamfight_participation`, `camps_stacked`).
  Прогноз: `|LL(B_noOD) − LL(B)| < 0,0005` на ≥ 5/6. Опровергается, если `B_noOD − B > +0,001` на ≥ 2 целях.
  Решение: не опровергнуто → боевая модель без этих колонок (перекос убран по построению, сборщик не нужен);
  опровергнуто → нужен ночной сборщик OpenDota.

## 2. Сверка сервинга с офлайн-сборщиком

`base/kills_v3_serving.py` строит состояние (`build-state`) проигрыванием той же истории `History`, что и
сборщик `base/tools/kills_v3_research.py`, и отдаёт 152 колонки на карту (`features_for_map`).

| проверка | результат |
|---|---|
| синтетика: 18 комбинаций среза/задержки × ~195 карт | 0 расхождений (в памяти, после загрузки, независимый оракул) |
| фазз hard-verifier: 48 конфигураций, 2 291 запрос вне порядка, 1 082 граничных | 0 расхождений |
| **реальные данные**: срез 2026-09-01, задержка 1200 с, 857 карт после среза | **max_abs_diff 0,0, 0 расхождений NaN** |
| пик RSS сборщика / build-state | 2,32 ГБ / 3,33 ГБ (строить только локально) |
| файл состояния / RSS после загрузки / загрузка | 227 МБ / 888 МБ / 1,4 с |
| `features_for_map` | 3,41 мс на запрос |

Дефекты, найденные реальной сверкой (значения признаков не меняли):
1. `save_state` писал метаданные с `sort_keys=True` и переставлял источники → ложный отказ `parity` при > 1
   источнике. Теперь `source_order` хранится явно (схема v2).
2. Валидация отвергала отрицательные team ID, но в корпусе STRATZ они настоящие (`radiantTeam.id`: 394 504
   ячейки, 18,6% карт 2026 года); сборщик использует их как обычные ключи. Теперь принимается любой int64,
   0 — «нет команды». Живой хелпер `_match_team_id` обрезает их до 0, поэтому контекст shadow парсит ID сам.
3. SHA кода снимался в конце сборки (8 мин), а не при импорте → состояние, собранное кодом 31de1e31, получило
   SHA файла, изменённого посреди сборки. Теперь SHA фиксируется при импорте.
4. Живые карты приходят в порядке конца драфта, а не старта; при задержке 24 ч ожидающих событий ~сутки, и
   прежний отказ на «не по порядку» выключал бы shadow за часы. Теперь `strict=False` использует уже применённый
   фронт и пишет `overvisible_s` (минуты, будущего не видит); `parity` работает с `strict=True`.

## 3. Рычаг задержки: B_d86400 против B_d1200 (26 016 тестовых карт, парный бутстреп по дням, 2 000 повторов)

| цель | B24 − B12 LL [95% ДИ] | B24 − A | B24 − прод | AUC прод → B12 → B24 |
|---|---|---|---|---|
| w_5_15 | −0,00089 [−0,00186, +0,00014] | −0,00237 | −0,00245 | 0,6784 → 0,6799 → 0,6823 |
| w_10_20 | +0,00059 [−0,00017, +0,00133] | −0,00256 | −0,00228 | 0,6705 → 0,6759 → 0,6741 |
| w_15_25 | +0,00031 [−0,00039, +0,00102] | −0,00251 | −0,00229 | 0,6590 → 0,6644 → 0,6649 |
| w_20_30 | −0,00015 [−0,00108, +0,00074] | −0,00227 | −0,00210 | 0,6412 → 0,6448 → 0,6463 |
| rad_30_25 | +0,00191 [+0,00110, +0,00274] | −0,00216 | −0,00253 | 0,7330 → 0,7397 → 0,7368 |
| total_55_50 | +0,00095 [0,0, +0,00180] | −0,00401 | −0,00410 | 0,7439 → 0,7513 → 0,7494 |

**0/6 целей хуже порога +0,002 → d86400 не опровергнут.** A воспроизводится бит в бит между прогонами
(max |Δ| = 0). Оговорка: `pro_corpus_rich.npz` пересобран между сборками d1200 (sha d40cb576…) и d86400
(sha dfd75b97…); сравнение на одних и тех же 26 016 картах.

**Механизм.** Цена задержки почти целиком — невидимость предыдущей карты той же серии:

| цель | карты с предыдущей картой серии < 24 ч (n ≈ 3 500, 14,5%) | остальные (n ≈ 20 500) |
|---|---|---|
| total_55_50 | +0,00681 | −0,00004 |
| rad_30_25 | +0,00392 | +0,00156 |
| w_5_15 | +0,00283 | −0,00152 |
| w_10_20 | +0,00199 | +0,00035 |
| w_15_25 / w_20_30 | +0,00043 / −0,00105 | +0,00029 / 0,00000 |

Следствие: подкачка в состояние только что доигранных карт серии (живой пайплайн их знает через ~20 мин)
вернула бы ~0,007 LL на total для 14,5% карт. Это отдельный рычаг; в этот выкат не входит.

Свежесть источника: в `pro_corpus_rich.npz` на момент ночной сборки за последние 24 ч 33 карты (обычно ~38 в
сутки), минутные ряды пропущены у 0% — лаг STRATZ в корпусе на режим d86400 не влияет.

**Решение: режим сервинга — модель, обученная с задержкой 86 400 с, + ночной снимок состояния.**

## 4. Перекос источников OpenDota (найден чтением кода)

Метрики 16..20 `PLAYER_METRICS` (варды, сентри, станы, участие в драках, стаки) приходят только из разовых
выгрузок OpenDota (`opendota_windows_20260919/20260923`); регулярного сборщика нет, а STRATZ-корпус
пересобирается каждую ночь (`base/tools/kills_v3_research.py:38-42,65-86,125-145`). В бою у всех карт после
23.09 эти метрики пусты, и 30 из 152 колонок (`player_*_{метрика}_{sum,mean,effective_n_mean}`) постепенно
устаревают. Офлайн-замер этого не видит — выгрузки покрывают всю историю. Отсюда абляция (§5).

## 6. Shadow

`base/kv3_shadow.py` (коммит e7d2386d): при `KV3_SHADOW_ENABLED=1` строка панели + признаки kills-v3 считаются
моделью B в фоновом потоке и пишутся в `runtime/kv3_shadow.jsonl` рядом с вероятностями прода; полные векторы —
в `runtime/kv3_shadow_features.jsonl` для перескоринга других кандидатов. Вердикты, текст панели и ставки не
меняются. Независимая проверка (native hard-verifier): ядро ACCEPT; shadow FIX_REQUIRED (отрицательные team ID
обрезались) → исправлено → ACCEPT по дельте. Ночная сборка состояния — `scripts/ops/build_kv3_state.sh`
(коммит 2f4de838), доставка на serv1 только при маркере `runtime/kv3_state_deliver.on`.

## 8. Где искать ошибку

- **Сверка прошла, а в бою признаки другие.** Сверка идёт на тех же исходниках и том же коде. В бою: другие
  team ID в живом фиде (хелпер обрезал отрицательные — поэтому свой парсер в контексте shadow), `startDateTime`
  в другой единице, аккаунты 0 у скрытых профилей. Смотреть `kv3_finite_share`, `x_panel_nan_share`,
  `start_ts_source` в журнале shadow и перескорить векторы из `kv3_shadow_features.jsonl`.
- **Linux/Python 3.12 против macOS/3.9 не сверялись бит в бит**: `sum()` в 3.12 — Нейман (0/200 000 расхождений
  после float32 на синтетике), libm `exp`/`pow` не проверены. Закрывается запуском `parity` на serv1.
- **Рычаг задержки** сравнивает два прогона на разных версиях корпуса (sha d40cb576… и dfd75b97…). Если
  результат окажется у порога — пересобрать d1200 на текущем корпусе.
- **Механизм «предыдущая карта серии»** посчитан по `series_ids`/`ends` из od3_full_d1200; разрез после факта,
  не пререгистрирован.
- **Порядок запросов**: при `strict=False` запрос может увидеть события, закончившиеся до старта более поздней
  уже посчитанной карты минус задержка (минуты). В журнале это `overvisible_s`; если там часы — ошибка.
