# E-280. Проверка по сохранённым прогнозам

Запрос: модель регулярно ошибается на высокой уверенности и кажется повторением
ELO. Аудит читает production и исходные результаты. Обучение, изменение порогов,
деплой и рестарт не выполнялись. Рабочая версия прода на момент проверки —
`99b1bb8`, PID `554767`.

## Метод и покрытие

- Источник прогнозов: сохранённый `runtime/prematch_model_bet_sent.jsonl`
  с реальным match ID, временем, стороной, confidence, account-ELO и expected WR.
  281 строка превращается в **202 карты**: берётся первая отправка по реальному
  ID, суффикс `.0/.7` и меняющийся `map_num` не создают новые наблюдения.
- Исходы: `didRadiantWin` из `7.41e_part*.json` (176 карт), дополненные
  `radiant_won` из сохранённых `stratz_team_matches.json` и
  `prematch_live_delta.json` (ещё 11). Конфликтов победителя между источниками нет.
  ELO application ledger не используется как источник меток.
- 15 ID не найдены. Ещё ID `8968286637` исключён: время отправки позднее
  рассчитанного окончания `startDateTime + durationSeconds`. Итого **186/202**.
  Полные списки исключений и SHA256 входов — в `audit.json`.
- Это отобранные отправленные сигналы. По умолчанию самостоятельную ставку
  разрешают только `full,no_org` (`WIN_MODEL_VETO_PREMATCH_BRANCHES`). В журнале
  eval 753 строки, в том числе 81 `no_account_no_org`, но нет match ID.
  Поэтому статистику отправок нельзя переносить на все показанные карточки.
- Для атрибуции соединяем eval с отправкой только при единственном совпадении
  пары команд, индекса (разница <0.002) и предшествующего времени в пределах
  300 секунд. Для 48 карт есть однозначные `parts`; остальные не реконструируем
  сегодняшним артефактом или сегодняшним ELO.

## Сравнение с ELO на тех же картах

Берём **знак записанного `model_elo`**, то есть разницы account-ELO. Это простой
выбор победителя, а не отдельно обученная или откалиброванная ELO-only модель
и не прямое сравнение с сегодняшним общим блоком командного ELO в Telegram.

- ML: **140/186 = 75.3%**; account-ELO: **141/186 = 75.8%**.
- Направление совпадает на **165/186 = 88.7%** карт.
- На 21 расхождении ML права 10 раз, account-ELO — 11.

На этом отобранном наборе добавка ML к направлению account-ELO не видна.
Разница в одну карту не доказывает превосходство ELO и не измеряет качество
ранжирования вероятностей или прибыльность.

На 48 картах с точным разложением средние доли абсолютных групповых вкладов:
ELO 40.2%, draft 32.4%, players 25.4%, h2h 2.0%. ELO — крупнейшая группа
на 20/48. Это не подтверждает, что **каждое** решение состоит почти целиком
из ELO. Группа `elo` объединяет account-ELO, `opp_elo`, взаимодействия и
`hybrid_strength`; доли групп не являются независимыми вероятностями.

## Конкретные карточки и контракты

1. Пример пользователя — **8992864996, Yangon Galacticos — DIREBORN**.
   Записано Dire 72.465%, ветка `full`, вклады -0.6249/-0.3708/-0.063/-0.0552.
   Источник результата: `radiant_won=false`; эта карта выиграна Dire.
2. Подтверждённая уверенная ошибка — **8992777443, Team Nemesis — InterActive
   Philippines**, Radiant 83.7%, ELO +60%, draft -20%, players +16%, h2h +4%.
   Победила Dire. Карты нет в журнале самостоятельных отправленных ML-сигналов.
   В текущем кэше 13 завершённых карточек с прогнозом: 11 верных; при ≥80% — 5/6.
   Этот короткий кэш не является независимым вторым историческим тестом.
3. **Процент в строке — raw sigmoid**, `index=(p-0.5)*100`; empirical calibration
   не преобразует показываемый процент. `SERIES_SURPRISE_CORRECTION` выключен
   по умолчанию и отсутствует в окружении текущего процесса.
4. **«Вход 100%» относится к выбранной ветке.** Ветка `full` использует 35
   признаков, `no_account_no_org` — 7, `rating_only` — 1; ветки без account
   получают `filled=1.0` по построению. Карточка не показывает это различие.
5. **Несогласованность цены:** formatter (`base/cyberscore_try.py:7529`)
   вызывает общую `lan_min_odds(confidence)` и не учитывает branch. Для
   `no_org` ветка отправки использует собственный WR. Например при 88%:
   UI 1.22, собственная таблица no_org WR=0.815785 → порог отправки 1.23.
   Для `no_account_no_org` при 72.5% показывается 1.42, хотя её сохранённый
   branch WR=0.765746; самостоятельные ставки этой ветки по умолчанию запрещены.
6. Не смешивать разные таблицы: `lan_winrate()` даёт **кумулятивный** WR выше
   порога из `LAN_THRESHOLDS`; `lan_expected_wr()` — значение точечной сетки
   `LAN_ODDS_GRID`. Для full 72.5% journal `wr=0.777`, а отправленный
   `expected_wr=0.7057`; это разные популяции, не расхождение sigmoid.

Артефакт на диске сервера: `data/prematch_model_artifact_v3.npz`, snapshot
`1789085068`, SHA256 `352318cf34ce713299fad551912bbf536c309560066c4ffeb3ecf8495db9e25a`.
Хеш фиксирует текущий файл; журнал не хранит идентичность артефакта каждого
исторического прогноза. `get_model()` кэширует объект до перезапуска процесса.

## Воспроизведение и где искать ошибку

Сохранить приватные журналы/кэши serv1 в `runtime/artifacts/misc/ml-confidence-20260911/`
без изменения production. Запуск из корня проекта:

```sh
venv_catboost/bin/python3 scripts/ops/audit_prematch_confidence.py runtime/artifacts/misc/ml-confidence-20260911 --corpus pro_heroes_data/json_parts_split_from_object
venv_catboost/bin/python3 -m pytest base/tests/test_prematch_confidence_audit.py -q
```

Проверки: 2 regression tests — повтор одной карты с разными poll/map_num,
ориентация победителя, исключение поздней записи, отказ от неоднозначной атрибуции.

Ограничения: 15 отсутствующих исходов могут менять результат; отбор отправок
может скрывать ошибки карточек; модель/ростеры/турниры менялись за месяц;
метки STRATZ сверены между локальными источниками, не с независимым провайдером.
Время `ts-startDateTime` часто около 15 минут (медиана 923 секунды), тогда как
в журнале `game_time=-79` на 122/186 строках: это разные часы/возможная задержка,
поэтому считать набор доказанным сигналом до фактического старта нельзя.
Нельзя оценивать доходность по `min_odds`: исполненная цена не записана.
Утренний дефект ELO-rebase мог затрагивать признаки; здесь используются ровно
сохранённые значения, причинность ошибок этим аудитом не установлена.

Следующий обоснованный шаг: журнал **всех** показанных прогнозов с match ID,
branch, идентичностью артефакта, исходным p, применяемой калибровкой и фактическим
временем; единый formatter ветки и явная полнота доступных данных. После этого —
сравнение полной модели с ELO-only на свежем общем наборе. Убирать ELO или
подгонять калибровку под эти 186 исходов оснований нет.
