# E-313 — индивидуальная и контекстная история игроков

22.09.2026. Offline, продолжение E-311 по запросу пользователя.

## Гипотеза и протокол до запуска

E-311 добавлял в основном средние последних 20 карт. Новый эксперимент проверяет,
поможет ли сохранить различия между пятью игроками и учитывать условия прошлых
карт. Это две фиксированные добавки к E-311 performance-only, без нового поиска
гиперпараметров:

- `individual`: 80 колонок — отклонение статистики игрока на выбранном герое
  от его общей статистики, отдельно по каждой из пяти ролей обеих команд.
  Те же 8 показателей, последние 20 игр, shrinkage `n/(n+10)`, что в E-311.
- `context`: individual + 190 колонок. XPM, LH/min, hero damage/min и tower
  damage/min сначала переводятся в log1p-разность с игроком противоположной
  команды в той же оценённой роли. Вычитается историческая норма героя/роли,
  с поправкой на патч. Ещё один показатель — результат прошлой карты минус
  предматчевая вероятность K24. Для каждого игрока сохраняются last20 mean,
  hero20 residual и recent5-minus20, counts и свежесть практики.

Нормы героя/роли — последние 500 завершённых наблюдений перед началом самой
исторической карты. Патчевая норма сглаживается к общей через `n/(n+20)`.
После расчёта исторического наблюдения оно доступно следующей query только
при `source.end < query.start`. Текущий результат или текущая статистика
никогда не входят в признаки этой же карты. Missing остаётся NaN.

Recipe `lgb31_all`, два прежних June/early-July fold, embargo 1 час и series
purge. Сравнение на тех же 9018 картах с E-311 performance, E-308 ансамблем
и K24. Исходный критерий сильного улучшения: >=5 п.п. к K24, нижняя граница
парного series-bootstrap95 >0 и меньший log loss. Критерий не меняется.
Выбор между двумя arms: accuracy, затем log loss. Если ни один не улучшает
одновременно WR и log loss E-311, сохраняется прежний кандидат.

Это исследованная selection-выборка. August–September terminal не переоткрывается
для выбора. Новый независимый результат потребует будущих карт после фиксации
варианта. Никакое дообучение на всех метках не считается проверкой качества.

## Источники и ограничения

Individual использует все 16 036 007 player rows сохранённого E-311 source.
Context использует лишь карты, которые можно связать с E-309 reference cohort
по MID/account/hero/end. Для них известна предматчевая вероятность K24 и
порядок ролей, рассчитанный до карты. Это оценённые роли, **не фактические
позиции текущего матча и не установленные соперники по линии**.

Патч назначается по `base/dota_patch_calendar.py`: announcement timestamp для
7.41–7.41e, legacy UTC-midnight для более ранних записей. Bucket 0 означает
неизвестный патч; патчевая история для него не собирается. Реальная версия
клиента каждой карты и историческое время публикации API не подтверждены.
Нормализация performance не является поправкой на индивидуальный Elo каждого
соперника: используется сравнение с той же ролью и отдельный win-minus-K24.

## Харнесс и команды

`base/tools/prematch_player_context.py --mode build --dataset E309.npz
--source performance_source.bin --output-dir NEW_DIR --threads N` сохраняет
`individual.npz`, `context.npz`, `context_observations.npz`, `metrics.json`.

`--mode experiment --dataset E309.npz --performance E311/performance.npz
--features BUILD_DIR --arm individual|context --draft FROZEN_DRAFT1.npz
--draft FROZEN_DRAFT2.npz --output-dir NEW_DIR --threads N` сохраняет
validation probabilities, обе fold-модели и проверяет точное воспроизведение
прогнозов после повторной загрузки.

Полные commands, hashes и frozen protocol:
`runtime/artifacts/elo/general_ml_context_20260922/`.
Запуск через `.orchestra/runtime/orchestra.py resources preflight/run`;
неизменяемые snapshots, отдельный новый output directory на job.

## Где искать ошибку

Проверять **обе** временные границы: прошлые наблюдения для нормирования
исторической карты и завершение самой карты перед целевой query. Отдельно
проверять account/hero/role ключи, equal-end границу, патч 0, перенос игроков
между слотами, сторону win residual, восстановление E-311 mean из individual,
сохранение categorical indices при добавлении колонок и одинаковые MID/y/Elo.
Большой полный corpus не означает такое же покрытие контекстной истории.

## Проверки и исполнение

36 регрессий прошли: прямой brute-force oracle для rolling, perturbation
текущих/будущих stats и outcomes, source join, границы патча, перестановка
сторон и восстановление E-311 агрегатов. Независимое ревью не нашло
блокирующих дефектов. Full build связал 12 614 650 player rows с 1 261 465
картами reference cohort без пропущенных связей. Доля конечных context values
71.9736%; наличие исходной записи не гарантирует достаточную прошлую историю.

Отдельный oracle проверил 8170 значений на 43 картах (включая три Daxak),
максимальное расхождение 7.63e-7. Это проверка history aggregation по сохранённым
observations; нормализация observations отдельно покрыта регрессионным oracle.

После трёх отказов CPU preflight пользователь явно разрешил временно считать
одним процессом/потоком с nice=10. Исходные bytes ресурсов сохранены в
`runtime/artifacts/elo/general_ml_context_20260922/resources.before.json`;
отдельная квитанция хранит исходный и временный SHA. Production не менялся.
После завершения всех трёх recovery jobs исходные bytes восстановлены;
SHA `0491d63bded2e28da52ff2eaae4b9d4a31eb74dc62f5a9575565270e4d3f3f44`.
Квитанция `resource_restoration.json`; чужая активная кампания сохраняет свои
параметры, захваченные при запуске.

У context fit exit code 0, но первая кампания завершилась ошибкой
`snapshot_input_missing`: каталог frozen inputs исчез к заключительной проверке.
Причина/исполнитель удаления не установлены; эта задача ничего не удаляла.
Исходная failed receipt сохранена и не заменена успешной. Все 12 исходных файлов
по-прежнему совпали с начальными SHA. Новая независимая сборка всех 9018 eval
строк и native Booster replay дали точное совпадение обоих fold-прогнозов.
Новая проверка прошла с `snapshot_verified_after=true`; это не восстанавливает
утраченную post-run проверку исходного обучения задним числом.

Дополнительный Elo-only контроль зафиксирован до получения E313 метрик:
logistic C=1 на K24 logit, только прошлые eligible Elo rows, те же completion
embargo, series purge, half-life365 и league weights. В обоих folds исключены
262 924 training rows без доступного Elo. Калибровка не использует eval labels.
Она не меняет заранее заданные ML arms и правило их сравнения. Первая попытка
этого контроля истекла в очереди до старта; следующий запуск завершился успешно.

## Результаты

Оба фиксированных варианта завершены. Независимая арифметика проверила
тождество MID/y/series/K24, 9018 уникальных карт, pooled metrics и оба folds.
У individual обе сохранённые модели воспроизводят прогнозы точно, пересечения
train/eval серий отсутствуют, post-run snapshot verification прошла.

| Вариант | Верных / 9018 | Accuracy | Log loss |
|---|---:|---:|---:|
| K24 | 5522 | 61.2331% | 0.64430371 |
| Калиброванный K24 | 5556 | 61.6101% | 0.64335908 |
| E-308 прежний ансамбль | 5834 | 64.6928% | 0.62369211 |
| E-311 performance | 5844 | 64.8037% | 0.62240383 |
| E-313 individual | 5842 | 64.7815% | 0.62299180 |
| E-313 context | 5845 | 64.8148% | 0.62161543 |

Context против E-311: 338 исправленных ошибок и 337 новых; чистый прирост
одна карта, **+0.0111 п.п.**, series-bootstrap95 **[-0.5465; +0.5606] п.п.**
Выигрыш log loss 0.0007884, CI [-0.0013920; +0.0028373]. Individual против
E-311: 326 исправлений и 328 ухудшений, -0.0222 п.п., CI [-0.5825; +0.5316].

Context против calibrated K24: **+3.2047 п.п.**, CI [2.1835; 4.2130];
на 2199 расхождениях ML права 1244 раза, Elo — 955 (56.57% / 43.43%).
Выигрыш log loss 0.02174365, CI [0.01609205; 0.02745775]. Против raw K24
+3.5817 п.п., CI [2.5537; 4.6181]. Bootstrap: 4000 выборок целых серий,
seed20260921; карты без series группируются по MID.

Заранее заданное правило точечного выбора выбирает context. Это не доказанное
улучшение относительно E-311: оба CI включают ноль. Fold-модели сохранены как
offline-кандидат; дополнительный all-label refit и production promotion не
выполнялись — проверенный эффект не оправдывает замену рабочего артефакта.
Полный пересчёт: `runtime/experiments/elo/general_ml_context_20260922/compare.py
run-12979f6a1e1e1cd865509959
.orchestra/jobs/run-12979f6a1e1e1cd865509959/01-elo-calibration/output/validation.npz`;
выход `runtime/artifacts/elo/general_ml_context_20260922/comparison.json`.

Это прежняя selection-выборка, не новый независимый тест. Критерий сильного
прироста контекстным вариантом не пройден. Возраст игроков и достоверные
фактические позиции этим экспериментом не добавлены.

### Разбор слабого прироста

В двух context fits на `league_category` приходится 40.89% / 40.15% training
gain и 47.91% / 47.12% разбиений. На 270 новых individual/context признаков —
около 0.36% gain. Проверка имён и индексов подтвердила: 637 numeric, затем
10 hero categories и league на индексе 647; смещения колонок нет. Training
importance не измеряет независимый вклад в качество и не доказывает причину
слабого прироста.

Post-hoc разрез по доступной до fold истории турнира дал смешанный результат.
На 2544 картах новых турниров context угадал 1794, E-311 — 1809, calibrated
K24 — 1735. Это противоречит объяснению «весь результат — запоминание ID
турниров»: ML обходит Elo и на новых ID, но новая контекстная добавка там
ухудшает accuracy. Разрезы не являются новым критерием выбора модели.
Таблицы: `training_league_audit.json`, `context_training_importance.json`,
`league_transfer_audit.json` в каталоге E313. Последний воспроизводится командой
`OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 venv_catboost/bin/python3 -m
runtime.experiments.elo.general_ml_context_20260922.audit_league_transfer`.

Следующая проверяемая гипотеза — парный E-311/context fit без predictor
`league_category`, с сохранением league для исходных eligibility и weights.
Она **не запускалась** и не входит в исходные два E313 arms. Вмешательство
необходимо, прежде чем приписывать слабый lift ID турнира.
На момент завершения доступно около 1.3 GiB, уже есть другая очередь вычислений;
новый snapshot данных потребует около 1.8 GiB плюс outputs. Новые большие
запуски не назначены, файлы не удалялись. Это ограничение следующего эксперимента,
не объяснение наблюдённого слабого качества текущих вариантов.
