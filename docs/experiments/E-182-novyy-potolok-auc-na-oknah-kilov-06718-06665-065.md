# E-182. Новый потолок на окнах килов и рецепт воспроизведения

- **Дата:** 2026-08-14 (alex: «зафиксируй новый auc для килов и как его воспроизвести»)

## 1. Результат

| окно | база (35 боевых) | **новый результат** | Δ |
|---|---|---|---|
| 10-20 | 0.6393 | **0.6641** | **+0.0248** |
| 15-25 | 0.6358 | **0.6546** | **+0.0188** |
| 20-30 | 0.6258 | **0.6395** | **+0.0137** |

> **Исправление 14.08.** Первая версия этой записи давала 0.6718 / 0.6665 / 0.6531.
> Числа были получены на НЕВЕРНОЙ цели: `rk` и `dk` в корпусе — это НАКОПЛЕННЫЕ
> килы (ряды монотонны, `rk.sum(1)=453` при `rk[-1]=32`), а я суммировал их по
> окну вместо взятия разности на границах. На проверочной карте правильная
> разность «рад 8, дайр 9» даёт −1, а суммирование давало +13 — противоположный
> знак. Цель исправлена на `rk[b] − rk[a]`, числа выше — верные.

Цель — знак разницы килов сторон в окне; карты с нулевой разницей и короче
конца окна исключены. Отобрано 414 колонок для 10-20 и 20-30, 200 для 15-25.

Прибавка не случайна: на валидации она росла монотонно с числом признаков —
для 10-20 это 0.6411 → 0.6549 → 0.6593 → 0.6623 → 0.6618 → 0.6626 при 0, 25,
50, 100, 200, 414 добавленных колонках.

**Ориентир, но не строгое сравнение.** По замеру E-164 продовый словарь `ed`
давал на про 0.6464 / 0.6290 / 0.6272. Здесь выше по всем трём окнам, однако
словарь на ЭТОЙ же выборке не мерился — числа взяты из прошлой записи. Строгое
сравнение на одной выборке ещё предстоит, и оно обязательно до любого внедрения.

## 2. Из чего собран вход

**База (35 колонок)** — боевой набор предматчевой модели, тот же, что даёт 0.7181
на победе. Берётся из `prematch_model_artifact_v3_hybrid.npz` через
`audit_live_path.train_columns`.

**Симметричный блок (414 колонок после отсева постоянных)** — из
`base/pregame_features.py`: командные суммы констант героя и baseline
`герой×позиция`, поданные парами `X_diff = A − B` и `X_sum = A + B`.

## 3. Три вещи, без которых цифра развалится

**Baseline героев должны быть собраны ДО границы теста.** Использован
`base/hero_baselines_protest.json` — окно 180 дней, заканчивающееся ровно на
`TEST_FROM`. Набор по патчу 7.41 брать нельзя: 7.41 начинается 24.03, тест —
29.03, и baseline знали бы исходы теста. Цена такой подмены измерена на
драфт-логите в E-177: +0.0025 из воздуха.

**Число признаков подбирается на валидации, а не на тесте.** Последние 20%
обучающего окна по времени отложены; на них выбирается K, и лишь потом модель
переобучается на всём обучении и один раз меряется на тесте.

**Данные выровнены на прежний набор карт.** 14.08 ночная цепочка пересобрала
выжимки корпуса, и он вырос с 482 486 до 1 260 250 карт, а кэши признаков
(`EXT`, драфт-логит, `G`) остались на старом наборе. Скрипт восстанавливает
прежний порядок по `mids` из `hybrid_features.npz` — единственного кэша, который
их сохранил. Контроль правильности выравнивания: база обязана воспроизвести
боевые **0.7181** на победе; если получилось другое — выравнивание сломано, и
числа по килам недействительны.

## 5. Что мешает считать это готовым к внедрению

1. **Словарь не мерился на этой выборке.** Сравнение с 0.6464/0.6290/0.6272 —
   указательное. Нужен прогон словаря `ed` на тех же 25 366 / 24 281 / 21 352
   картах.
2. **Мерялось на всех картах подряд, а не на боевом отборе.** По E-172 гейты,
   выбранные на словарной выборке, на прод-отбор не переносятся; то же может
   случиться и здесь.
3. **Кэши признаков отстают от корпуса втрое** (482 486 против 1 260 250).
   Пересборка даст и больше данных для обучения, и снимет необходимость
   выравнивания — но это несколько часов счёта.
4. **Боевого пути для этих признаков нет.** `pregame_features.py` умеет считать
   их на один матч, но в живой пайплайн килов они не заведены.
