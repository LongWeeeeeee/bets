# E-263. Продолжение E-262: исправление данных до выбора формулы

## Реализовано

1. `MatchRecord` сохраняет `duration_seconds`. `result_timestamp` определён
   только для положительного целого значения; отсутствующий/невалидный конец
   никогда не подменяется стартом. Загрузчик также отвергает неположительные,
   boolean и общие между сторонами account ID.
2. `replay_events` объединяет начала и окончания карт. Все прогнозы на t идут
   **до** результатов, закончившихся в t. Обновление использует актуальное
   состояние на момент наблюдения исхода; expectation пересчитывается в этот
   момент, как в live, а не извлекается из будущего снимка. `process_match`
   получает копию записи с timestamp результата; исходный start сохраняется
   в исторической записи для прогноза.
3. Snapshot, map evaluation и series evaluation используют этот порядок.
   Sweep-бонус становится доступен только после окончания всех наблюдаемых
   карт серии; при неизвестной длительности бонус не применяется. Live
   подтверждённые исходы обновляют модель по времени наблюдения, не по
   устаревшему времени регистрации карты.
4. `attach_league_tiers_asof` использует прошлых участников лиги и текущую
   пару; ровесники с тем же start добавляются после всей группы. Глобальные
   roster/tier таблицы команд остаются фиксированными prior — это ограничение,
   а не восстановленная историческая экспертная оценка.
5. ELO и `sort_pub_matches_by_patch.py` читают
   `base/dota_patch_calendar.py`. Для 7.41–7.41e приняты **точные времена
   официальных объявлений Steam**, не произвольная полночь. Legacy-границы
   до 7.40c сохранены. `base/keys.py` с другими событиями и потребителями не
   изменялся; название source-файла остаётся provenance, модельный reset
   определяется общим календарём по времени.
6. `ensure_snapshot`/`load_live_snapshot` и быстрые пути ML/panel отказываются
   от несовместимых `rating_replay_version`/`rating_calendar_signature`.
   Pin не отменяет миграцию; live-запрос не запускает многогигабайтный rebuild
   как побочное действие. Для перехода нужен явный offline `build_snapshot`.
   Поле `meta.model_config_signature` нового снимка теперь является подписью
   точной базы: конфиг, replay, календарь и история (исходы, составы, роли,
   tier и времена). Поэтому старые progress/full-state/delta не подходят
   даже при неизменном последнем timestamp. Старый `load_snapshot` сохранён
   для низкоуровневого аудита legacy-файлов.

## Воспроизводимость и ресурсный результат

Перед прогоном проверены все три машины (`scripts/ops/capacity.sh`).
Выбрана локальная машина с 16 ГБ RAM и свободными CPU; serv1 не нагружался.
Raw-корпус скопирован через APFS clone в `runtime/artifacts/elo/endtime_replay_20260905/source`.
Исходный сборщик может продолжать работать, не меняя этот вход.

Первый запуск PID 9320 остановлен адресным SIGTERM (exit 143): `json.load`
разворачивал 500-МБ файлы целиком и упёрся в память. Отчётов/рейтингов этот
запуск не опубликовал. После перехода `load_matches` на `ijson.kvitems`
(уже установленный pinned dependency, backend `yajl2_c`) raw разбирается по
одной карте. `progress(path, count)` сообщает окончание каждого файла.
Продолжение PID 13088 читает ту же копию; лог `replay_streaming.log`.

Два варианта получают одинаковые карты, календарь, tier-priors и config:
`finished` применяет только завершённые исходы; `start_control` намеренно
оставляет прежнее обновление после группы стартов. K24 player Elo тоже
пересчитывается на том же потоке. Модели создаются последовательно, без
одновременного хранения двух больших состояний. Peak RSS около 5.5 ГБ,
один replay 1395380 карт занимает около трёх минут после загрузки.

Сохраняются `inputs.json`, `finished.npz`, `start_control.npz`, `report.json`.
Кэши требуют совпадения fingerprint исходного корпуса, config, календаря и
исходников, включая `domain.py` с семантикой результата. Изменение файла
корпуса во время загрузки приводит к отказу до публикации итогов.

## Проверки и где искать ошибку

- Регрессии: overlapping maps, одинаковые времена старта/окончания,
  unknown/invalid duration, prefix-tier, все границы календаря, pinned legacy,
  изменение исхода при том же watermark с отклонением delta/progress/state,
  streaming loader с progress и не-object root, быстрый panel-путь.
- Расширенная проверка: `venv_catboost/bin/python3 -m pytest ELO/tests/
  base/tests/test_dota_patch_calendar.py base/tests/test_team_elo_contract.py
  base/tests/test_hybrid_block_freshness.py base/tests/test_elo_snapshot_caches.py
  base/tests/test_win_model_veto.py base/tests/test_live_elo_applied_before_verdict.py
  base/tests/test_live_elo_winner_lookup_map_match.py base/tests/test_live_elo_batch_applied_logging.py
  base/tests/test_prematch_live_delta.py -q` дала 193 passed и 3 посторонних
  падения старого `test_win_model_veto`: `_unknown_seen`, `_alias_draft_features`,
  `served_model` отсутствовали уже в pre-turn `78ff97d` (проверено AST из git).
  Добавленные после этого 3 loader/CLI-теста прошли отдельно; CLI проверяет
  дедупликацию пересекающихся частей архива до общего replay.
- Не путать время окончания игры с публикацией исхода в API. В архиве
  нет исторических задержек Stratz/пуллинга и времени блокировки драфта;
  результат `start + duration` — ранняя оценка доступности, live применяет
  результат по фактическому времени его наблюдения.
- Тест после 12 августа свежее прежнего **кэша рейтингов**; он не объявляется
  гарантированно никогда не изучавшимся корпусом. Январь–август уже использовался
  в прошлых исследованиях. Калибровка каждого окна обучается только на 120
  предыдущих днях с `end < cutoff`, а общие test-series исключаются из train.
- Все выводы — про рейтинговые вероятности. Отбор ставок, кэфы и полный
  обученный стек не пересчитывались; локальные изменения не выложены в прод.
- Исходные истории здесь одинаковые для двух контролей и Elo. Популяция
  отличается от матрицы 482486 карт E-262: нельзя напрямую приписать изменение
  абсолютной метрики между двумя записями качеству исправления.

## Результаты

На **63778 картах** четырёх окон 2026 года:

| Вариант | Log loss ↓ | Brier ↓ | AUC ↑ |
|---|---:|---:|---:|
| Hybrid, контроль на старте | 0.654683 | 0.231747 | 0.651294 |
| Hybrid, после окончания | 0.654665 | 0.231739 | 0.651326 |
| K24 Elo, после окончания | 0.653080 | 0.231141 | 0.652053 |
| Hybrid + калибровка | 0.653185 | 0.231075 | 0.651273 |
| K24 Elo + калибровка | 0.651831 | 0.230549 | 0.652030 |
| Hybrid + контекст | 0.652691 | 0.230846 | 0.652206 |
| Elo + hybrid + контекст | 0.651314 | 0.230297 | 0.653399 |

Свежий участок **2026-08-12 — 2026-09-04**, 776 карт; train 36587 карт за предшествующие 120 суток:

| Вариант | Log loss ↓ | 95% ДИ разницы с raw hybrid |
|---|---:|---|
| Hybrid, после окончания | 0.619397 | [+0.000000, +0.000000] |
| K24 Elo, после окончания | 0.613933 | [-0.016697, +0.004545] |
| Hybrid + калибровка | 0.621515 | [-0.001479, +0.005697] |
| Hybrid + контекст | 0.622038 | [-0.002251, +0.007184] |
| Elo + hybrid + контекст | 0.615708 | [-0.012202, +0.003890] |

**Обновление вывода E-262:** одинаковая история меняет сравнение: простой K24 Elo здесь имеет меньший log loss во всех четырёх окнах. Это не доказывает преимущество замены признака в полной ML-модели: там Elo и hybrid могут дополнять друг друга. На новом маленьком окне интервалы всех кандидатов пересекают ноль, а калибровка hybrid ухудшила log loss. Её старые коэффициенты не переносятся в боевые артефакты.

Само устранение start-time утечки даёт почти нулевой эффект на loss: 0.654683 → 0.654665. Это исправление достоверности, а не доказательство заметного повышения точности. Этот контроль НЕ изолирует эффект общего календаря и исправления глобального порядка серий: календарь/prefix-tier уже одинаковы в обоих плечах.

Оба replay завершились с exit 0; `DONE .../report.json` в логе. Peak RSS 5553 МБ. Текущие config/боевые веса не подбирались по test.

Результат: exit 0, **19 реальных составов, max feature error = 0**; 31 карточка

ELO состава с прежней формулой ML-признака на одном состоянии, не измерение
точности. Явные отсутствующие пути исключают действующие live overlays.
Новый снимок не заменял действующий, production не менялся. Для выкладки
нужны согласованные код и пересборка снимка по актуальному корпусу сервера;
одна замена кода приведёт к отклонению legacy-снимка.
