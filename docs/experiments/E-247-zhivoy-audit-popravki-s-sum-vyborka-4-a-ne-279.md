# E-247. Живой аудит поправки s_sum на продолжениях серий: боевая выборка n=4, а не 279

- **Дата:** 2026-09-02. Задача измерить, помогает ли `logit(p) += 0.215 * s_sum`
  реальным боевым вердиктам на картах 2+ серии — третья, «решающая» точка после
  офлайн-аудита 22.08 (+0.0123 AUC [+0.0035; +0.0212] на 25 892 боевых вердиктах
  скорера) и replay на 20 продолжениях (Brier 0.2258 → 0.2288, хуже).
- **Вопрос:** улучшает ли поправка боевые предматчевые вердикты на картах 2+
  серии, измеренные ПРЯМО из прод-лога (не офлайн-скорер, не replay), и какой
  вес был бы оптимален на этой же выборке.
- **Харнесс:** `runtime/experiments/cyberscore-prod/series_surprise_e247/analyze.py`,
  входы `shadow_lines_raw.txt` (grep прод-лога) и `applied_maps.csv`
  (`live_elo_progress.json` → `.applied_maps`), метод дедупа и джойна — в
  `README.md` того же каталога.
- **Запуск:** `venv_catboost/bin/python3 runtime/experiments/cyberscore-prod/series_surprise_e247/analyze.py`
- **Дефекты, найденные ДО выводов:**
  1. **Прод-лог короче, чем предполагала постановка задачи.** `grep -c
     SERIES_SURPRISE_SHADOW` на serv1 и локальная копия сходятся на 134
     строках, не 406. `head -1` 204-мегабайтного файла — это баннер старта
     процесса (`cyberscore_try.py is running outside venv_catboost...`),
     то есть файл пересоздан заново при последнем рестарте, а не копится с
     22.08. За последние двое суток в git 5 коммитов (включая
     `7aa993f` «late-гейт»), каждый из которых по правилам проекта требует
     рестарта прода в том же ходу — любой из них обнулил лог. 406 строк были
     реальны на каком-то более раннем срезе; сейчас их не существует, бэкапа
     лога на сервере нет (`ls cyberscore_sourcetv.log*` — один файл).
  2. **Суффикс `map_key` (`dltv.org/matches/<id>.<N>`) — не индекс карты.**
     Внутри одной серии `N` растёт с пропусками (пример: серия 8962964580 —
     N=0,1,4,5,6), что соответствует общему для всех серий счётчику опросов
     живого трекера, а не позиции карты в серии. Дедуп по группировке
     «последняя строка на стем» (стем = `series=`, он же `match_id` в
     `applied_maps` — известный дефект E-224: у прода нет id карты, весь
     ряд серии несёт один номер) безопасен НА ЭТОЙ выборке (ни один стем не
     откатывается к меньшему N внутри окна), но не доказан как общее правило:
     у `applied_maps` есть контрпример — стем 8978544633 несёт ДВЕ записи,
     `.0`→radiant_win=true и `.49`→false, с разницей в 270 секунд (слишком
     мало для двух настоящих карт, но исходы противоречат друг другу — либо
     это реально разные карты, либо трекер один раз перепутал сторону).
     Все 4 серии, попавшие в выборку n_prev>=1, — без этого дефекта: там,
     где стем встречается в `applied_maps` больше одного раза, все записи
     согласны по `radiant_win` (харнесс явно это проверяет и исключил бы
     несогласный стем, `ambiguous=[]` в текущем прогоне).
  3. **Прямой join по строке `map_key` находит только 22 из 134** (эти два
     трекера порождают суффикс независимо). Join сделан по СТЕМУ (числовой
     части), без суффикса — см. `README.md`.
- **Результат:**

  | метрика | до (p_rad) | после (0.215·s_sum) | Δ (после−до) | ДИ95 Δ (bootstrap, 1000, по сериям) |
  |---|---|---|---|---|
  | log-loss | 0.5895 | 0.6299 | +0.0404 | [+0.0075; +0.0766] |
  | Brier | 0.2133 | 0.2325 | +0.0192 | [+0.0038; +0.0361] |
  | AUC | 1.000 | 0.667 | −0.333 | ДИ AUC до [1.00;1.00], после [0.00;1.00] (n_pos=3,n_neg=1 — вырождено) |

  n=4 (все продолжения серии с известным исходом, дедуп + джойн см. выше).
  Разбивка n_prev==1 (n=3): log-loss 0.6379→0.6861, Brier 0.2414→0.2645.
  n_prev>=2 (n=1, серия 8974898633): log-loss 0.4443→0.4611, Brier
  0.1287→0.1365 — одна точка, не интервал.
  Калибровка по трём полосам вырождена почти до одного наблюдения на полосу
  (n=2/1/1 до коррекции, n=3/0/1 после) — печатать средние по полосе с n=1
  как «калибровку» было бы имитацией точности, реальные числа — в выводе
  харнесса, а не в этой таблице.
  Перебор веса 0.00…0.40 шагом 0.05 минимизацией log-loss: оптимум на точечной
  выборке w=0.00 (log-loss 0.5895, ниже чем при любом w>0); бутстрап
  показывает w=0.00 в 997/1000 передискретизаций, ДИ95 оптимума [0.00; 0.00].
  Вес 0.215 не близок к оптимуму этой выборки.
- **Контроль (проверка знака).** Ориентация `s_sum` — к радианту ТЕКУЩЕЙ карты,
  как того требует дизайн (docstring `base/series_surprise_shadow.py:27-30`).
  Подтверждено кодом: `surprise_from_maps` (`:104-129`) считает вклад карты
  как «победила ли команда `radiant_team_id` минус обещанная ей вероятность»
  для параметра — радианта, который передаёт вызывающий; `last_surprise`
  (`:212-244`) при чтении переворачивает знак, если при исходном расчёте
  радиантом была другая команда пары (`:237`: `sign = 1.0 if
  rec["radiant_team_id"] == rad else -1.0`), то есть возвращаемое значение
  ВСЕГДА ориентировано на радианта запроса — на текущую карту. Дефектов в
  знаке не найдено.
- **Где искать ошибку:** n=4 — это не выборка, это четыре точки; ДИ95 честно
  посчитан бутстрапом, но при 4 уникальных наблюдениях с возвращением
  различимых передискретизаций не больше 35 (C(4+4-1,4)), так что «точность»
  интервала иллюзорна — он в разы уже, чем должен бы быть при реальной
  вариативности. AUC на n_pos=3/n_neg=1 меняется квантами по 1/3, «0.667»
  значит буквально «один из трёх выигрышных попал в минус» — не устойчивая
  оценка. Единственный источник исходов — `applied_maps` того же живого
  трекера, который сам совершает ошибки (см. дефект 2 выше, стем 8978544633);
  независимая сверка с локальным про-корпусом не делалась — все 4 карты
  слишком свежи (28.08–02.09.2026), корпус столько ещё не переварил. Окно —
  часы одного дня, не 136 суток офлайн-аудита; сезонность/патч/мета не
  контролируются вовсе.
- **Вывод:** поправку `logit(p) += 0.215*s_sum` в боевой индекс НЕ вводить —
  `series_surprise_shadow` остаётся теневым модулем (он и сейчас ничего не
  решает, только пишет `s_sum`/`s_last`/`n_prev` в лог рядом с живым индексом,
  `base/series_surprise_shadow.py:11-13`). Живой замер n=4 не может подтвердить
  ни опровергнуть офлайн-аудит статистически, но третий раз подряд (после
  replay на 20 картах) указывает в сторону «хуже», и оптимальный вес на живых
  данных — ноль, а не 0.215. Решение: не вводить, пока не накопится живой лог
  БЕЗ рестартов — повторить этот харнесс через 1-2 недели непрерывной работы
  `SERIES_SURPRISE_SHADOW` без обнуления лога, целясь на n_prev>=1 порядка
  нескольких десятков карт.
