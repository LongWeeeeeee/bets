# E-262. Формула, обновления и достоверность вероятностей ELO

## Что действительно считается

При текущем конфиге и serving-контракте E-173/E-261 сила состава равна
`S = 0.68 * mean(player_global) + 0.32 * mean(player_local[TIER3])`.
Вес собственно roster-компонента равен **нулю** (`max_roster_weight=0`),
org-prior выключен, роли для TIER3 выключены. Название hybrid не означает,
что прямо сейчас в итоговое число добавляется оценка сыгранности пятёрки.
Состав влияет через выбранных игроков и темп их обновления.

Теоретическая вероятность: `p = 1 / (1 + 10 ** (-delta / 400))`.
Обновление игроков использует `K * (actual - expected)`. Присвоить одинаковое
обновление всем пяти игрокам корректно: среднее пятёрки изменится на один
`K * error`, а не на пять. Коэффициенты обучения зависят от tier и свежести
состава; это модельные предположения, а не универсальная формула Elo.

Снимок `ELO/output/live_team_elo_snapshot.json` на момент аудита имел конфиг,
совпадающий с `HybridEloConfig()`. Decay рейтингов выключен. Настройка
`bo3_sweep_bonus_weight=0.05` используется в series evaluator, но не в
штатных `build_snapshot`/live `process_match`: её наличие в JSON не доказывает
работу бонуса в боевом рейтинге.

## Доказанный дефект и исправление

`_build_snapshot_dict` раньше обходил `series_bundles`, затем все карты каждой
серии. Серии сортируются по старту: A1(t=10), A2(t=100), B1(t=50) применялись
именно так. Даже при разных игроках это меняет общий `side_bias` тира, а
также может возвращать модель через границы патчей назад. Минимальный repro
дал B1 вероятность 0.50430792 вместо хронологической 0.50215866.

Теперь модель обновляется по единому дедуплицированному потоку
`(timestamp, match_id)`. Агрегаты серий считаются отдельно. Регрессионный тест
сравнивает полное состояние снимка с моделью, полученной глобально
хронологическим обходом перемежающихся серий. Аналогичный порядок событий
исправлен в `run_series_online_evaluation`: прогнозы начала серий до обновлений
того же timestamp, бонус за sweep после последней карты, а не до чужой
промежуточной карты.

**Это исправление требует пересборки снимка.** Уже накопленное состояние не
исправляется заменой Python-файла. В этом ходе ни снимок, ни runtime, ни
боевые веса не заменялись; deployment не выполнялся.

## Протокол сравнения

- Рейтинги берутся из предматчевых исторических кэшей, а не из текущего
  снимка, уже видевшего исходы. Общая популяция и исходы одинаковые.
- Используемая колонка hybrid из base matrix сверена в точности с
  `hybrid_strength_tier3.npz` по match ID на всём train/test диапазоне.
  В старой части до сентября 2019 есть 14152 fallback-строки другой формы;
  ни одна из них в обучение калибровки или оценку здесь не входит.
- Окна: январь–февраль (11005 карт), март–май (19790), июнь–11 августа
  (12139). Перед каждым — обучение калибровки на 120 днях строго до границы.
  Серии, присутствующие в тесте, исключены из обучения.
- Одна логистика `C=1`, нормировка только по train. Нет перебора коэффициентов
  по test. Форма `p = sigmoid(b + a * delta / 400 + c * prev)`;
  `prev` равен +1/-1 относительно Radiant при известной предыдущей карте,
  иначе 0. Варианты используют соответствующие подмножества колонок.
- Контекст строится на полном rich-корпусе по префиксу истории: совпадают
  серия и пара team ID, предыдущая карта закончилась строго до текущего
  старта (`start + duration < now`), разрыв не больше трёх суток.
  Нет отбора по будущей полноте серии или итоговому счёту. Стороны могут
  меняться, победитель разрешается через команду на конкретной карте.
- Метрики: log loss, Brier, AUC и accuracy; парный bootstrap log loss по
  сериям, 1000 повторов. Для неизвестной серии каждый match ID — свой кластер.
- Артефакт сохраняет границы/размеры окон, веса калибровок, статистики входных
  файлов, SHA256 последовательности mids, общие и контекстные метрики.
  При изменении входного файла во время прогона итоговый отчёт не публикуется.

## Результаты

Меньший log loss/Brier лучше; больший AUC лучше. Это качество рейтинговых
прогнозов на всех выбранных картах, а не всей ML-модели или ставок.

| Вариант | Log loss | Brier | AUC |
|---|---:|---:|---:|
| Elo, прямая формула | 0.656230 | 0.232613 | 0.644892 |
| Hybrid, прямая формула | 0.654786 | 0.231810 | 0.651224 |
| Elo, калибровка | 0.655006 | 0.232028 | 0.644889 |
| Hybrid, калибровка | 0.653028 | 0.231035 | 0.651172 |
| Glicko, калибровка | 0.652770 | 0.231202 | 0.646577 |
| Elo + hybrid | 0.652329 | 0.230774 | 0.651617 |
| Hybrid + контекст | 0.652679 | 0.230885 | 0.651634 |
| Elo + hybrid + контекст | 0.652054 | 0.230653 | 0.651993 |

Для hybrid калибровка улучшила log loss в **3/3** окнах. Разница против raw:
−0.001759, парный 95% ДИ [−0.002446, −0.001078]. Коэффициент при `delta/400`
получился 1.9662 / 1.9504 / 1.9644 против фиксированного `ln(10)=2.3026`:
прямая шкала в этой популяции слишком уверенная. Есть и Radiant-intercept
0.104–0.124. Нельзя просто скопировать эти числа в боевой конфиг: сначала
нужна новая проверка на корректно восстановленном состоянии и свежих данных.

Glicko выигрывает у калиброванного hybrid в январе–феврале и июне–августе,
проигрывает в марте–мае. Его ДИ разницы с raw hybrid [−0.004459,+0.000356]
пересекает ноль. Универсальной победы замены модели здесь нет.

В контексте предыдущей законченной карты всего 6440 строк. Там raw hybrid
loss=0.652804, calibrated=0.648671, hybrid+context=0.645767. На всём наборе
добавка контекста невелика. Это другая популяция, чем отобранные полные BO3
фаворитов с разрывом >=50 из E-256: переносить их −16 п.п. сюда нельзя.

## Где искать ошибку и что не доказано

1. **Это повторный исторический тест.** На этих датах уже оценивались другие
   идеи. Результат не является untouched holdout, подтверждением ROI или
   разрешением автоматически заменить модель. E-229 отдельно показал,
   что небольшой выигрыш Glicko по AUC не улучшил отбор ставок.
2. **Исходы в кэшированных рейтингах обновлялись по времени старта.**
   Строгий `asof < start` не доказывает, что предыдущая карта уже закончилась.
   Исправленный порядок snapshot также пока использует старт. Для точного
   live replay нужны события завершения, затем пересборка признаков. В новом
   контексте previous-map время завершения уже проверяется.
3. **Исходные истории рейтингов различаются.** Hybrid обучался на расширенном
   raw-потоке, старые Elo/Glicko — на своих корпусах. Здесь сравниваются
   имеющиеся признаки, а не изолированный эффект формулы при одинаковом
   исходном обучающем потоке. Калибровка одного hybrid контролирует этот риск
   лучше прямого сравнения разных систем.
4. **Календарь patch-reset устарел:** `ELO/models.py` заканчивается на 7.40c
   (2026-01-21), хотя source-patch снимка — 7.41e. `exact` reset после этой
   границы не срабатывает. Это не исправлялось догадкой о датах: в проекте
   существуют несовпадающие таблицы патчей. Нужен проверенный календарь,
   единый для raw-разметки и model reset, и последующий replay.
5. **Tier-классификация** старых builders использует глобальный состав лиги и
   текущую справочную таблицу команд. Этот аудит не доказывает доступность
   таких tier-признаков на историческую дату. Точные claims о качестве
   восстановленного live пути требуют отдельной проверки этих данных.
6. Glicko здесь — существующая адаптация по игрокам против средней команды.
   Это не доказательство качества канонического Glicko-2 или TrueSkill.
   В старом TrueSkill-коде шум результата команды задан `2*beta²` при сумме
   навыков десяти игроков; стандартная независимая player-performance
   конструкция требует суммы шумов участвующих игроков. Не менять обученный
   признак молча и не считать прежний отрицательный тест опровержением всей
   семьи TrueSkill.

## Вывод для следующей модели

Проверка кода: `venv_catboost/bin/python3 -m pytest ELO/tests/
base/tests/test_team_elo_contract.py base/tests/test_hybrid_block_freshness.py
base/tests/test_elo_snapshot_caches.py -q` — **120 passed**.
`py_compile` изменённых модулей и `git diff --check` прошли.
Полная `base/tests/` повторно не запускалась: этот ход ограничен ELO;
предыдущий полный прогон E-261 содержал посторонние падения.

Сначала исправить воспроизведение истории и источник patch-reset, затем
пересобрать состояние/признаки и проверить свежий временной отрезок. В качестве
простого кандидата сохранить hybrid и обучать его перевод в вероятность;
контекст серии проверять дополнительным признаком. Объединение Elo и hybrid
можно оставить внутренним ML-признаком, показывая пользователю один
канонический рейтинг состава и отдельно итоговую вероятность модели.

Glicko добавляет неопределённость рейтинга, Glicko-2 также моделирует
волатильность; TrueSkill умеет выводить навыки игроков из командного исхода.
Это полезные конструкции, но ни одна не гарантирует меньшую ошибку на наших
данных. Первичные описания:
[Glickman, Glicko](https://www.glicko.net/glicko/glicko.pdf),
[Glickman, Glicko-2](https://www.glicko.net/glicko/glicko2.pdf),
[Microsoft, TrueSkill](https://www.microsoft.com/en-us/research/publication/trueskilltm-a-bayesian-skill-rating-system/).
