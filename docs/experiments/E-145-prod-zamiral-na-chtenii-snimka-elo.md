# E-145. Прод замирал на чтении снимка ELO

- **Дата:** 2026-08-13 (alex: «я всё ещё не могу через tail_log получить вторую
  карту boomboys»)

## 1. Три версии подряд оказались неверными

Проверялись и отпали: группировка карточек в `tail_log` (починена в
`cb52ccf`, но записи всё равно не было), фильтр лиг в мосту, «прод не успевает
дойти до третьего матча». Последняя выглядела подтверждённой — в хвосте лога
было 2 блока `SourceTV match #` при трёх живых матчах, — но это оказался
артефакт короткого окна: на полном логе `голов == блоков` во всех циклах.

## 2. Матч был в мосту и не был у прода

`sourcetv_probe` завёл матч в 07:56:30 и удалил в 08:53:56. Монитор Winline,
читающий тот же `runtime/sourcetv_matches.json`, видел его **20 раз** с 08:19
по 08:52 — с корректной картой:

```
{"match_id": 8943055466, "team1": "OG", "team2": "BoomBoys", "map_num": 2}
```

В логе прода за те же 57 минут `grep -c 8943055466` = **0**.

## 3. Причина: main-thread стоял в чтении файла

```
Thread 3082097 (idle): "MainThread"
    read_text (pathlib.py:1030)
    _load_roster_history_cached (base/team_kills25_shadow.py:343)
    load_roster_history -> build_roster_kills_context -> record_shadow_observation
    _record_team_kills25_shadow_candidate (base/cyberscore_try.py:6031)
    check_head -> general
```

`STAT=Dsl` (непрерываемое ожидание диска), CPU 3:43 за 41:47 аптайма,
RSS 4.0 ГБ + `VmSwap` 6.85 ГБ, своп машины 8191/8191 МБ.

Файл — `ELO/output/live_team_elo_snapshot.json`, **349 МБ**. Читателей два:
`ELO/live_team_strength.py` (кладёт в `_SNAPSHOT_CACHE`) и
`base/team_kills25_shadow.py` (свой `lru_cache`). История килов лежит ВНУТРИ
снимка ELO, поэтому shadow-модуль разворачивал вторую независимую копию той же
структуры. Отсюда ~11 ГБ на 16-ГБ машине и своп-трэшинг.

Независимое подтверждение из журнала вердиктов: дыра **08:38:20 -> 09:25:58**,
ровно окно жизни второй карты BoomBoys.

## 4. Что сделано

`load_roster_history` берёт готовый объект из `live_team_strength._SNAPSHOT_CACHE`,
если путь совпадает, и файл повторно не парсит. Плюс потолок
`TEAM_KILLS27_ROSTER_HISTORY_MAX_MB` (64 МБ): файл крупнее в живой путь не
берётся, контекст ростера деградирует до `history_unavailable` (штатная ветка
`build_roster_kills_context`), а не вешает цикл. Тесты: 23 passed на serv1.

| замер | до | после |
|---|---|---|
| RSS прода | 4.0 ГБ | 2.8-3.6 ГБ |
| VmSwap прода | 6.85 ГБ | 4.9-5.4 ГБ |
| своп машины | 8191/8191 | 7040/8191 |
| длина цикла | 5-19 мин, заморозки до 33 мин | 50-100 c |
| живых матчей в цикле | 1 из 2-3 | все |

## 5. Остаток

Снимок по-прежнему разворачивается в живом процессе. Замер границы:
`team_kills_history_by_team_id` начинается на байте 34 748 278 из 365 578 581 —
история килов это **90%** файла, собственно ELO ≈ 35 МБ. Правильное решение —
разнести артефакты (ELO отдельно, история отдельно); тогда потолок 64 МБ сам
отсечёт историю от живого пути. Требует правки писателя снимка
(`TEAM_KILLS_HISTORY_MATCHES_PER_TEAM = 100` в `ELO/live_team_strength.py`) и
ребилда — решение за alex.
