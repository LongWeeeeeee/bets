# E-249. ELO-снимок на проде отстал на 22 суток

- **Дата:** 2026-09-02. Запрос alex: «что насчет наших ml моделей наших
  экспериментов и фич к ним? может у нас не оптимальный конфиг или какие-то из
  фич не доходят не обновляются. Я бы хотел чтобы после каждой карты мы были с
  актуальной информацией по предыдущему матчу в наших фичах», затем «делай все»
  на предложенный план из пяти пунктов. Этот пункт — третий (живая свежесть
  ростер-истории kills27).

## Что найдено

- `TEAM_KILLS25_ROSTER_HISTORY_PATH` указывает на `ELO/output/live_team_elo_snapshot.json`
  (`base/team_kills25_shadow.py:34-35,337-344`). На проде файл имел mtime 20.08
  и `meta.reference_utc = 2026-08-11T19:26:02+00:00`, `loaded_matches = 569 493`,
  `data_dir` — одноразовый scratchpad `corpus_freeze`. Локальный корпус к этому
  моменту: 1 395 282 матча, срез 01.09 20:51 UTC.
- Следствие: kills27-shadow, который на проде **включён и шлёт рекомендации в
  Telegram** (`RUNTIME_RULES.md:30,33`), считал «последние 30 карт с overlap
  состава >= 4» и latest-patch выборку по истории, обрезанной 11.08.
  `team_kills_history_latest_patch` в проде был старше 7.41e.
- Живой слой (`runtime/live_elo_progress.json`, 497 применённых карт) обновляет
  рейтинги, но НЕ ростер-историю: `applied_maps` несёт только
  `{series_key, winner_slot, radiant_win, applied_at, match_id}` — без team_id,
  килов и составов, поэтому «живая накладка» поверх истории из прогресса
  невозможна в принципе. Правильный фикс — пересборка и доставка снимка.
- Доставка снимка не входила в ночную цепочку: `rebuild_prematch_snapshot.sh`
  возил предматчевый артефакт, панельные снимки и алиасы, а ELO-снимок остался
  на ручной доставке («перенесён файлом» — комментарий в юните). Ручное =
  протухает молча: никакой проверки возраста не было.

## Замер перед доставкой

Пересборка `ELO/live_team_strength.py` на текущем корпусе: 11 минут
(19:24 -> 19:35), 131 728 команд, 87 431 с историей килов, 646 МБ
(продовый был 242 МБ), `latest_patch = 7.41e`, мета байт-в-байт совпала с
локальной сборкой того же дня 12:46 — сборка детерминирована.

Главный риск доставки — не свежесть, а смена базы: корпус вырос x2.45, и
рейтинги могли бы стать несопоставимыми (а `hybrid_strength` — один из двух
признаков предматчевой модели с корреляцией 1.0 к обучению). Проверено на
tier1/tier2 по `team_id`:

| показатель | значение |
|---|---|
| общих team_id (tier1/2) | 376 (прод 394, свежий 402) |
| медиана дельты силы | **+0.17** |
| среднее | +3.00 |
| sd | 23.33 |
| min / max | -66.4 / +230.8 |
| только прод / только свежий | 18 / 26 |

Крупные дельты — это НЕ дрейф базы, а команды, которых прод-срез не видел:
у team_id 10019843 прод-`last_seen` 12.07, у свежего 01.09 (+230.8);
10150413 — 30.05 против 21.08 (+144.8). То есть снимок возвращает ровно ту
информацию, которой не хватало.

## Действие

1. Бэкап прод-снимка: `ELO/output/live_team_elo_snapshot.json.bak_20260902_ref0811` (242 МБ).
2. Доставка tmp + `mv` (rebuild-then-replace), sha1 `93f9ffc96edd48079b6978967707e8e449f35fcd` совпал на обеих сторонах.
3. Рестарт прода 19:43:32 (MainPID 2423476, NRestarts=0) — `_SNAPSHOT_CACHE`
   грузится один раз без ключа по mtime (`ELO/live_team_strength.py:1358-1369`),
   поэтому новый файл без рестарта не подхватывается.
4. Двойного счёта карт нет: при смене `base_reference_timestamp` прогресс
   сбрасывается в пустой (`ELO/live_team_strength.py:566-573`), а новый срез
   корпуса уже содержит те 497 карт.
5. Шаг 5c в `scripts/run/rebuild_prematch_snapshot.sh`: пересборка + атомарная
   доставка со сверкой sha1 каждую ночь, отказ не рвёт цепочку.

## Как воспроизвести

```bash
# сборка (~11 мин)
venv_catboost/bin/python3 ELO/live_team_strength.py \
  --snapshot-path ELO/output/live_team_elo_snapshot.json

# сравнение рейтингов tier1/2 (прод против локального свежего)
ssh serv1 "/root/main/venv/bin/python3 -c \"
import json
d = json.load(open('/root/main/ELO/output/live_team_elo_snapshot.json'))
out = {}
for k, v in (d.get('teams_by_org_key') or {}).items():
    if isinstance(v, dict) and v.get('tier') in ('TIER1','TIER2'):
        out[str(v.get('team_id'))] = [round(float(v.get('current_strength') or v.get('raw_team_strength') or 0), 2), v.get('last_seen_utc','')[:10]]
print(json.dumps(out))\"" > /tmp/prod_tiers.json
# затем локально: загрузить /tmp/prod_tiers.json и свежий снимок, соединить по
# team_id, считать медиану/среднее/sd дельт и топ-8 по |дельта|
```

## Где искать ошибку

- **Рейтинги поехали после ночной пересборки.** Первым делом — медиана дельты
  tier1/2 (команда выше). Если медиана заметно не нулевая (|Δ| > ~5), корпус
  сменил популяцию, а не вырос: смотреть `pro_heroes_data/json_parts_split_from_object`
  (308 файлов на 02.09) и `topup_pro_corpus.sh` — не начал ли добор тянуть
  непровые карты.
- **kills27 перестал слать.** Снимок теперь 646 МБ, а fallback-лимит
  `TEAM_KILLS25_ROSTER_HISTORY_MAX_MB = 64` (`team_kills25_shadow.py:371-382`)
  такой файл отвергает. Рабочий путь — ТОЛЬКО общий кэш
  `_shared_elo_snapshot()` (`:385-409`): модуль `live_team_strength` должен быть
  загружен и держать тот же файл в `_SNAPSHOT_CACHE`. Если общий путь не
  сработал, shadow fail-closed: `load_artifact()`/`load_roster_history()` вернут
  None, отправок не будет вовсе. Поднимать лимит НЕЛЬЗЯ: независимая загрузка
  второй копии 646 МБ JSON — это ровно тот RSS-катастрофа (4 ГБ + 6.8 ГБ свопа,
  D-state), от которой общий кэш и вводили.
- **Двойной счёт карт.** После доставки нового среза `runtime/live_elo_progress.json`
  обязан сбросить `base_reference_timestamp` на новый срез и обнулить
  `applied_maps`. Если 497 (или больше) карт остались при новой базе — гард
  `live_team_strength.py:566-573` не сработал, рейтинги учитывают одни и те же
  карты дважды.
- **RAM на проде.** JSON 646 МБ в памяти процесса — примерно вдвое больше
  прежнего; пик юнита до доставки был 5.7 ГБ при 15 ГБ на машине. Смотреть
  `systemctl show cyberscore -p MemoryPeak` и drop-in `oom.conf`.
- **Снимок снова протух.** Шаг 5c не фатален, поэтому молчаливое протухание
  возможно: ловить его должен freshness-watchdog (возраст `meta.reference_utc`),
  а не эта цепочка.

## Отрицательная часть

Живая накладка ростер-истории из `live_elo_progress.json` НЕ построена: в
`applied_maps` нет ни team_id, ни килов, ни составов. Чтобы накладка стала
возможна, прогресс должен начать носить эти поля — это отдельная правка
`ELO/live_team_strength.py` с вопросом, нужна ли она вообще при nightly-доставке
(окно протухания сократилось с 22 суток до одних).
