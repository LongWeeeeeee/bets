# Сохранение живых результатов при пересборке ELO

## Инцидент 11.09.2026

На serv1 утренняя цепочка заменила ELO-снимок в 09:06 МСК, переписала
`runtime/live_elo_model_state.json` в 09:09 и собрала пустую дельту в 09:10.
При этом срез нового снимка — **03:37:50 МСК** (`1789087070`).
Прежняя перебазировка копировала только `model_state` нового снимка, а загрузчик
progress сбрасывал `pending_series` и `applied_maps` при смене базы.

В журнале есть успешные применения шести результатов после этого среза.
В кэшах Stratz и `prematch_live_delta.json` сохранились их исходы и десять

После пересборки `live_elo_delta.json` содержал `changes={}`, а `applied_maps`

Получение результата тоже имеет задержку: для первых двух карт

после первой карты Nemesis 2156 → 2159, InterActive 1906 → 1901.
Исправление перебазировки само по себе не ускоряет публикацию результатов.

Повторная проверка в 09:45 МСК показала новое применение карты `8992825325`
и непустую дельту с обновлениями десяти игроков. Процесс остался прежним
(`530488`, запуск в 09:11). Таким образом, обработка новых исходов работает,
но потерянные при пересборке шесть результатов не восстановлены. При ремонте
состояния нужно сохранить и этот более поздний результат.

## Контракт перебазировки

`ELO/live_team_strength.py` сохраняет у нового применённого результата полный
`match_record`, исход и время его применения моделью. При переходе на новый
срез состояние строится из нового снимка и результатов, которые в нём ещё
отсутствуют. Ожидающие карты сохраняются, если их ещё нет в снимке.

Время применения не доказывает отсутствие карты в срезе: запоздалый ответ
Stratz может касаться карты, уже попавшей в корпус. Поэтому новый снимок
содержит ограниченный список ID завершённых карт и границу его покрытия в
`meta.recent_completed_match_ids` и
`meta.recent_completed_match_ids_coverage_since`. Проверка использует точное
вхождение ID и временные границы; неоднозначность останавливает перебазировку
до записи файлов. Старые записи без достаточного контекста нельзя молча
отбросить или восстановить по одному имени команды.

CLI `ELO/rebase_runtime_model_state.py` принимает `--snapshot`, `--state` и
`--progress`. Все три пути относятся к одной операции. Повторный запуск на
той же базе сохраняет уже применённую дельту. Нормальный live-путь использует
ту же проверку при смене базы; прежний пустой progress не заменяет
неперенесённые результаты.

Запись завершённой карты отмечается в progress как незавершённая до сохранения
дельты или полного состояния. После сбоя следующий вызов восстанавливает
состояние из снимка и журнала результатов; обычная регистрация без такой
отметки не загружает большое полное состояние. Неоднозначная очередь,
в которой снимок покрывает лишь часть ожидающих карт, блокирует перенос:
старый счёт серии нельзя безопасно сопоставить с остатком очереди.

Для карт, уже учтённых снимком, progress хранит временные отметки дедупликации.
Их срок — семь дней от известного окончания карты либо первого подтверждения
снимком; следующая пересборка не продлевает срок. До истечения срока требуется
актуальное подтверждение ID новым снимком. Отсутствие подтверждения может
консервативно отклонить перенос, в том числе на границе окна покрытия.
Результат, который пришлось бы применить раньше или одновременно со срезом,
также отклоняется: время события не подменяется ради успешной пересборки.

`scripts/run/rebuild_prematch_snapshot.sh` доставляет новый снимок в `.tmp`.
После остановки сервиса он сначала выполняет безопасную перебазировку, затем
заменяет снимок и обновляет дельту/массивы. При отказе перебазировки снимок не
заменяется. CLI возвращает `1` при безопасном отказе с сохранённым прежним
состоянием; сервис запускается на прежнем снимке, цепочка возвращает ошибку.
Если откат не удался (`2`) или процесс аварийно прерван, сервис остаётся
остановленным до проверки целостности runtime-состояния.

## Проверка и восстановление

Регрессионные тесты находятся в `ELO/tests/test_runtime_state_memory.py` и
`ELO/tests/test_snapshot_delivery.py`. Проверяются перенос результатов,
повторный запуск, ID карт, уже учтённых снимком, сохранение ожидания и отказ без
перезаписи при недостаточном контексте. Доставка проверяется исполнением
реального shell-блока с изолированными заглушками команд.

Уже потерянные шесть результатов автоматически не появляются после установки
кода: их нужно отдельно восстановить из проверенных записей, повторно сверив
актуальный срез и применённые ID. До такого восстановления нельзя объявлять
текущие рейтинги полностью восстановленными. Деплой и изменение runtime-состояния
требуют разрешения оператора; диагностика инцидента не перезапускала сервис.
